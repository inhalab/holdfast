더 물어볼 만한 것 — 좌석에 어떻게 흩어지나, 성공이 도중에 멈추는 이유, 전환이 재기동인 이유, 첫 실행

요청은 좌석에 돌아가며 흩어진다. 1번 요청→1번 좌석, 2번 요청→2번 좌석… 좌석을 한 바퀴 돌면 다시 1번으로 온다. 전략을 걸면 좌석마다 홀드가 하나씩만 남고 나머지는 409이므로, 총 홀드는 정확히 좌석 수가 된다.

성공이 요청 수보다 한참 적은 것은 정상이다. 브라우저는 HTTP/1.1에서 호스트당 커넥션을 6개로 제한한다. 한 번에 떠 있는 요청은 6개뿐이고 나머지는 앞 요청이 끝난 뒤에 도착해 이미 잡힌 좌석을 만난다. 서버의 한계가 아니라 브라우저의 한계다 — 같은 실험을 스크립트로 보내면 none에서 요청 수만큼 홀드된다.

그래서 좌석 수가 6 이상이면 초과 홀드가 안 나온다. 동시에 떠 있는 요청 6개가 서로 다른 좌석으로 흩어져 애초에 겹치지 않기 때문이다. none과 전략의 차이를 보려면 좌석을 6개보다 적게 잡아야 하고, 1개가 가장 선명하다. 이것은 브라우저에서만 걸리는 제약이다 — 측정은 k6로 보내므로 좌석 1000개에서도 겹친다.

전략을 바꾸려면 앱을 다시 띄워야 한다. 전략 빈은 기동 시 하나만 만들어져 SeatHoldService에 직접 주입되므로, 런타임 교체는 측정 경로인 그 클래스를 고치는 일이 된다. 게다가 none은 부분 유니크 인덱스 U-2를 지워야 none이라, 전환은 앱만의 일도 아니다. ./holdfast strategy가 재기동과 인덱스 재적용을 함께 한다.

첫 실행은 한 번 눌러 버리고 시작하라. JVM이 데워지기 전 첫 묶음은 일부 요청이 연결 단계에서 실패한다.
