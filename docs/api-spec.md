# 예약 API 계약 — 요약과 설계 근거

**holdfast** — 좌석맵 조회부터 예약 취소까지의 HTTP 계약

기계가 읽는 정본은 [`docs/openapi.yaml`](openapi.yaml)이다. 이 문서는 그 요약과,
**왜 그렇게 정했는지**를 남긴다.

## 0. 이 문서의 목적

`docs/roles.md`가 1개월차에 "API 계약 확정"을 최건에게 배정한 이유는 하나다.
**박태준이 서버 구현을 기다리지 않고 화면을 만들 수 있어야 한다.**

따라서 요청·응답 스키마와 오류 코드는 **확정이다.** 이후 변경은 서버와 화면 작업을
동시에 깨뜨리고, k6 시나리오까지 함께 깨뜨린다. 바꿔야 한다면 코드보다 먼저
`openapi.yaml`을 PR로 고치고, 그 PR에 양쪽 담당자를 리뷰어로 붙인다.

## 1. 엔드포인트 요약

| 메서드 | 경로 | 용도 | 멱등키 | 사용자 헤더 |
|---|---|---|---|---|
| `GET` | `/api/sessions/{sessionId}/seats` | 좌석맵 전체 조회 (최초 1회) | — | — |
| `GET` | `/api/sessions/{sessionId}/seats/status` | 좌석 상태 스냅샷 (3초 폴링). `Accept`에 따라 JSON 또는 좌석맵 fragment — 5.3 | — | — |
| `POST` | `/api/holds` | 좌석 선점 (복수 좌석) | 필수 | 필수 |
| `DELETE` | `/api/holds/{holdId}` | 선점 해제 | 필수 | 필수 |
| `POST` | `/api/reservations` | 예약 확정 | 필수 | 필수 |
| `GET` | `/api/reservations/{reservationId}` | 예약 조회 | — | 필수 |
| `POST` | `/api/reservations/{reservationId}/cancel` | 예약 취소 | 필수 | 필수 |

폴링 엔드포인트는 지정된 6개에 더해 추가한 것이다. 근거는 5절에 있다.

### 1.1 정상 흐름

```
GET  /api/sessions/1001/seats              좌석맵을 받아 그린다
  └─ GET .../seats/status  (3초마다)       상태만 갱신한다

POST /api/holds                            좌석 3석 선점 → holdId, heldUntil
  ├─ 사용자가 취소 → DELETE /api/holds/{holdId}
  ├─ TTL 만료      → 서버가 자동 회수 (클라이언트는 카운트다운만 표시)
  └─ POST /api/reservations {holdId}       확정 → reservationId

GET  /api/reservations/{id}                예약 확인
POST /api/reservations/{id}/cancel         취소 → 좌석 반환
```

### 1.2 `holdId`와 `reservationId`

`erd.md` 4절은 `reservation` 행이 **홀드 시점에** 생성된다고 확정했다. 그러나 API는
확정 전까지 `reservationId`를 노출하지 않고 `holdId`만 준다.

**이는 의도된 설계이며 모순이 아니다. 내부 상태와 계약 표면을 분리한 것이다.**
`reservation` 행은 홀드 시점에 생성되지만, API는 **확정 응답에서만** `reservationId`를
노출한다. **클라이언트는 확정 전까지 `holdId`만 다룬다.**

홀드 단계의 예약 행은 `status = HELD`인 내부 상태이고, 클라이언트가 그 단계에서 다룰
대상은 "선점"이지 "예약"이 아니다. 식별자를 둘 다 주면 화면이 어느 쪽을 들고 있어야
하는지 모호해지고, 확정되지 않은 예약 ID가 밖으로 돌아다니게 된다.

| 단계 | 클라이언트가 다루는 식별자 | 서버 내부 `reservation.status` |
|---|---|---|
| 선점 직후 | `holdId` | `HELD` |
| 확정 후 | `reservationId` | `CONFIRMED` |
| 만료·해제 | (없음) | `EXPIRED` |

## 2. 확정된 전제 네 가지

**좌석 선택 상태는 클라이언트가 보관한다.** 서버 세션을 쓰지 않는다. 앱 2대 구성에서
세션 공유 문제가 생기고, 스티키 세션으로 우회하면 부하 분산이 왜곡되어 측정 자체가
오염된다 (`concurrency-spec.md` 0.4). 그래서 `POST /api/holds`의 응답에 `holdId`와
`seatIds`를 담아 돌려주고, **그 값을 잃어버리면 만료를 기다리는 수밖에 없다.**

**모든 상태 변경은 `Idempotency-Key`를 요구한다** (6절).

**409는 정상 거절이며 오류가 아니다** (3절).

**모든 시각은 서버 기준이다.** 응답마다 `serverTime`을 함께 준다. 예약 오픈 시각,
홀드 만료, 입장 가능 시간이 전부 시간 기반이라 클라이언트 시계를 신뢰하면 전부 조작
가능해진다 (`design-spec.md` 5.1). 홀드 응답에는 `expiresInSeconds`도 함께 주어,
화면이 시계 차이를 계산하지 않고 바로 카운트다운을 걸 수 있게 했다.

## 3. 오류 코드 — 정상 거절과 오류의 분리

`concurrency-spec.md` 7.1이 이 절의 근거다.

> **정상 거절과 오류를 반드시 분리한다.** 좌석이 이미 팔려 409를 반환한 것은 시스템이
> 제대로 동작한 것이다. 뭉뚱그리면 "실패율 40%" 같은 무의미한 숫자가 나온다.

그래서 HTTP 상태 코드만으로는 부족하다. 409 안에도 성격이 다른 것들이 섞이므로
**모든 오류 응답에 `code`를 실어 k6가 그 값으로 태깅해 집계한다.**

### 3.1 분류표

| `code` | HTTP | 분류 | 의미 |
|---|---|---|---|
| `SEAT_ALREADY_SOLD` | 409 | **정상 거절** | 좌석이 이미 팔림 |
| `SEAT_HELD_BY_OTHER` | 409 | **정상 거절** | 다른 사용자가 홀드 중 |
| `HOLD_EXPIRED` | 409 | **정상 거절** | 홀드가 만료됨 (CS-2·CS-3 경합) |
| `QUOTA_EXCEEDED` | 409 | **정상 거절** | 1인 최대 매수 초과 (CS-6) |
| `RESERVATION_NOT_OPEN` | 409 | **정상 거절** | 예약 오픈 전 |
| `LOCK_TIMEOUT` | 409 | **락 포기율** | 락 대기 시간 초과 — `pessimistic`·`redis` (`concurrency-spec` 7.6.1) |
| `RETRY_EXHAUSTED` | 409 | **락 포기율** | 재시도 상한 소진 — `optimistic` (`concurrency-spec` 7.6.1) |
| `HOLD_RELEASED` | 409 | 상태 거절 | 이미 해제된 홀드로 확정 시도 |
| `HOLD_ALREADY_CONFIRMED` | 409 | 상태 거절 | 이미 확정된 홀드 |
| `RESERVATION_ALREADY_CANCELLED` | 409 | 상태 거절 | (취소 API는 멱등이라 실제로는 200) |
| `RESERVATION_NOT_CANCELLABLE` | 409 | 상태 거절 | 입장 완료 등으로 취소 불가 |
| `IDEMPOTENCY_KEY_REUSED` | 409 | **클라이언트 오류** | 같은 키에 다른 본문 |
| `IDEMPOTENCY_KEY_IN_PROGRESS` | 409 | **클라이언트 오류** | 같은 키가 처리 중 |
| `VALIDATION_FAILED` | 400 | 클라이언트 오류 | 형식 오류·좌석 중복·빈 배열 |
| `SESSION_NOT_FOUND` | 404 | 클라이언트 오류 | 회차 없음 |
| `SEAT_NOT_IN_SESSION` | 404 | 클라이언트 오류 | 해당 회차의 좌석이 아님 |
| `HOLD_NOT_FOUND` | 404 | 클라이언트 오류 | 홀드 없음 |
| `RESERVATION_NOT_FOUND` | 404 | 클라이언트 오류 | 예약 없음 또는 남의 예약 |
| `INTERNAL_ERROR` | 500 | **서버 오류** | 서버 결함 |

### 3.2 집계 규칙

`concurrency-spec.md` 7.6 기록 양식의 두 열은 이렇게 채운다.

| 열 | 집계 대상 |
|---|---|
| 정상 거절률(409) | 위 표에서 **정상 거절**로 분류된 5개 코드만 |
| 락 포기율 | `LOCK_TIMEOUT`과 `RETRY_EXHAUSTED` 두 개만 |
| 오류율(5xx·타임아웃) | 5xx 응답과 네트워크 타임아웃만 |

**`LOCK_TIMEOUT`과 `RETRY_EXHAUSTED`는 409로 응답하지만 409율에 넣지 않는다.** 좌석이
팔려서 거절한 것이 아니라 좌석이 남아 있었을 수도 있는데 포기한 것이므로, 정상 거절도
오류도 아니다. `concurrency-spec.md` 7.6.1이 이 열의 정의와 해석 주의를 담고 있다.

**두 코드를 나눈 이유는 포기 사유가 전략마다 다르기 때문이다.** `LOCK_TIMEOUT`은 락
대기 시간(1초)을 넘긴 것이고(`pessimistic`·`redis`), `RETRY_EXHAUSTED`는 재시도 상한
3회를 소진한 것이다(`optimistic`). 하나의 코드로 합치면 시간 기반 포기와 횟수 기반
포기가 같은 이름으로 섞여, 보고서에서 어느 쪽인지 전략 열로 추론해야 한다. 두 코드는
같은 열(락 포기율)에 집계되지만 원인은 코드로 구분된다.

**상태 거절과 클라이언트 오류는 어느 쪽에도 넣지 않는다.** 부하 테스트에서 이 코드들이
나온다면 시나리오 자체가 잘못 짜인 것이므로, 별도 태그로 세어 두고 시나리오를 고치는
신호로 쓴다.

### 3.3 5xx와 절대 섞이지 않는다

**경합으로 인한 거절은 어떤 경우에도 5xx로 나가지 않는다.** 구현 시 아래를 지킨다.

- 낙관적 락 재시도 소진 → `RETRY_EXHAUSTED` (409). `OptimisticLockException`을 그대로
  전파해 500이 되게 두지 않는다. **`SEAT_HELD_BY_OTHER`로 반환하지 않는다** — 재시도를
  소진한 시점에 좌석이 실제로 남아 있었을 수도 있으므로 정상 거절로 세면 409율이
  오염된다(`concurrency-spec.md` 7.6.1).
- 유니크 제약 위반 → `SEAT_ALREADY_SOLD` 또는 `SEAT_HELD_BY_OTHER` (409).
  `DataIntegrityViolationException`이 500으로 새지 않게 명시적으로 잡는다
  (`concurrency-spec.md` 4.4).
- 비관적 락 대기 → 락을 얻거나 `LOCK_TIMEOUT` (409). Postgres `lock_timeout`은 1초로
  고정돼 있으므로(`concurrency-spec` 7.3) 그 예외를 잡아 409로 변환하고, 그대로 올려
  500이 되게 두지 않는다.
- 데드락 감지 → `LOCK_TIMEOUT` (409). Postgres가 한쪽을 죽이면
  `CannotAcquireLockException`으로 올라오고 공통 핸들러가 락 대기 초과와 같은
  코드로 변환한다. **앱 레벨 데드락 재시도는 두지 않는다** — 좌석 ID 오름차순
  획득(`concurrency-spec` 5.1)이 데드락 자체를 막는 장치이고, 실제로 5개 전략
  전부 0건이었다(7.2.1). 재시도를 두면 정렬이 새고 있어도 그것이 가려진다.

500이 나오는 경우는 DB·Redis 연결 상실이나 예상치 못한 버그뿐이다. **부하 테스트에서
500이 한 건이라도 나오면 그것은 측정값이 아니라 고쳐야 할 결함이다.**

### 3.4 오류 본문 형식

RFC 9457 Problem Details (`application/problem+json`)를 쓴다.

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "요청한 좌석 중 2석을 선점할 수 없습니다.",
  "code": "SEAT_HELD_BY_OTHER",
  "serverTime": "2026-09-01T04:16:19Z",
  "conflicts": [
    { "seatId": 30412, "code": "SEAT_ALREADY_SOLD" },
    { "seatId": 30415, "code": "SEAT_HELD_BY_OTHER" }
  ]
}
```

**커스텀 형식 대신 RFC 9457을 택한 이유는 형식이 하나로 유지되기 때문이다.**
Spring Boot 4는 처리되지 않은 예외를 이미 `ProblemDetail`로 내보낸다. 커스텀 봉투를
따로 만들면 우리가 잡은 오류와 프레임워크가 낸 오류의 모양이 달라져, 화면이 두 가지
형태를 모두 처리해야 한다.

`code`와 `serverTime`, `conflicts`는 RFC 9457이 허용하는 확장 필드다.
`detail`은 그대로 사용자에게 보여줄 수 있는 한국어 문장으로 채운다.

### 3.5 락 대기 상한 — 두 값 모두 1초

`LOCK_TIMEOUT`이 얼마나 자주 나오는지는 락 대기 상한이 정한다. 그 값은
`concurrency-spec.md` 7.3에 고정 변수로 못박혀 있다.

| 전략 | 설정 | 값 |
|---|---|---|
| `pessimistic` | Postgres `lock_timeout` | 1초 |
| `redis` | Redisson `waitTime` | 1초 |

**검수 기준 p95 3초 = 락 대기(최대 1초) + DB 처리 + 앱 처리 + 네트워크**라는 시간 예산에서
나온 값이다. 락 대기에만 3초를 주면 나머지에 쓸 예산이 남지 않아 고경합 시나리오에서
REQ-10을 구조적으로 달성할 수 없다.

`pessimistic`은 `lock_timeout`을 명시하지 않으면 무한 대기이며, 대기 중 DB 커넥션을 쥐고
있으므로 커넥션 풀이 먼저 마른다. 그러면 측정 대상이 락 경합에서 커넥션 고갈로 바뀐다.

## 4. 홀드는 전부 아니면 전무다

**결정: 요청한 좌석 중 하나라도 잡을 수 없으면 아무것도 잡지 않는다.** 부분 성공은
허용하지 않는다.

### 4.1 근거

**단일 트랜잭션·단일 락 순서와 일관된다.** `erd.md` 4.1과 `concurrency-spec.md` 5.1은
사용자 할당량 행 → 좌석 행(오름차순)이라는 전역 락 순서를 정해 두었다. 부분 성공을
허용하려면 좌석마다 트랜잭션을 쪼개 커밋해야 하는데, 그러면 전역 순서를 지켜도 데드락
회피의 의미가 사라진다. 순서를 정한 이유가 "한 트랜잭션 안에서 여러 좌석을 잡기
때문"인데, 트랜잭션을 쪼개면 그 전제가 없어진다.

**1인 최대 매수 검사가 원자성을 잃는다.** CS-6은 좌석 락 이전에 `user_session_quota`
행을 잠그고 `held_count`를 늘린다. 부분 성공이면 몇 개를 늘릴지가 좌석 획득 결과에
따라 달라지므로, 할당량 검사와 좌석 획득이 하나의 원자적 단위가 아니게 된다.
검사를 통과한 수량과 실제 보유 수량이 어긋난다.

**"정상 거절"의 정의가 모호해진다.** 3석 중 1석만 실패한 요청은 성공인가 거절인가.
어느 쪽으로 세든 `concurrency-spec.md` 7.1의 분리가 흐려지고, 7.6 비교표의 409율이
전략 간 비교 가능한 숫자가 아니게 된다. **측정 해석을 지키는 것이 이 결정의 가장 큰
이유다.**

**좌석 지정 예약에서 부분 성공은 제품으로서도 의미가 약하다.** 일행 3명이 흩어진
좌석을 받는 것은 대개 원하는 결과가 아니다.

**클라이언트 재시도 경로가 하나로 줄어든다.** 부분 성공을 허용하면 화면은 "무엇이
잡혔고 무엇이 안 잡혔는지"에 따라 상태를 재구성해야 한다. 전부 아니면 전무이면
성공이면 그대로 진행, 실패면 좌석을 다시 고르는 두 갈래뿐이다.

### 4.2 UX 손실을 보완하는 장치

전부 아니면 전무의 단점은 사용자가 "무엇 때문에 실패했는지" 모른다는 것이다. 그래서
409 응답에 `conflicts` 배열로 **좌석별 사유**를 함께 돌려준다.

```json
"conflicts": [
  { "seatId": 30412, "code": "SEAT_ALREADY_SOLD" },
  { "seatId": 30415, "code": "SEAT_HELD_BY_OTHER" }
]
```

화면은 이 좌석들만 빨갛게 표시하고 나머지 선택은 유지한 채 재시도를 유도할 수 있다.

`code`는 좌석별로 다를 수 있으므로, 최상위 `code`에는 가장 대표적인 사유 하나를 담는다.
**화면이 좌석별 처리를 할 때는 최상위 `code`가 아니라 `conflicts`를 봐야 한다.**

## 5. 좌석맵 폴링 — 왜 엔드포인트를 나눴나

`concurrency-spec.md` 0.4는 좌석맵 fragment만 3초 폴링한다고 확정했다. 그런데 전체
조회 응답을 3초마다 다시 보내는 것은 낭비다.

### 5.1 페이로드 차이

| | `GET .../seats` | `GET .../seats/status` |
|---|---|---|
| 호출 시점 | 화면 최초 진입 1회 | 3초마다 |
| 좌석 정적 정보 (`seatNo`·`rowIndex`·`colIndex`·구역) | 포함 | **제외** |
| 회차 메타 (`reserveOpensAt`·`maxPerUser`·`holdTtlSeconds`) | 포함 | **제외** |
| 좌석당 필드 수 | 6 | **2** (`seatId`, `status`) |
| `heldUntil` | 포함 | **제외** |
| 조건부 요청 | 없음 | `ETag` / `If-None-Match` → 304 |

**정적 정보는 회차 동안 변하지 않으므로 다시 보낼 이유가 없다.** 1000석 기준으로 좌석당
필드가 6개에서 2개로 줄고, 구역 계층과 회차 메타가 빠진다.

**`heldUntil`을 폴링에서 뺀 이유**는 두 가지다. 값이 매 초 달라져 `ETag`가 사실상 항상
바뀌므로 304의 이점이 사라지고, 남의 홀드가 언제 끝나는지는 화면에 필요 없다. 내 홀드의
만료는 `POST /api/holds` 응답의 `heldUntil`·`expiresInSeconds`로 이미 알고 있다.

### 5.2 `ETag`와 304

상태 스냅샷의 해시를 `ETag`로 주고, 다음 폴링에 `If-None-Match`로 되돌려 받는다.
좌석 상태가 그대로면 304와 빈 본문이 나간다. **예약 오픈 직후를 제외하면 3초 사이에
좌석 상태가 전혀 바뀌지 않는 구간이 대부분이므로**, 폴링 트래픽의 상당 부분이 빈 응답이
된다.

### 5.3 htmx와 JSON을 함께 지원한다

`Accept: text/html`이면 같은 데이터를 Thymeleaf 좌석맵 fragment로 렌더링해 반환한다.
htmx는 이쪽을 쓰고(`hx-get` + `hx-trigger="every 3s"`), k6와 다른 클라이언트는 JSON을
쓴다. **데이터와 판정 로직은 하나이고 표현만 둘이다.**

## 6. 멱등성

`concurrency-spec.md` 6절이 근거다. 상태를 바꾸는 네 요청 — 선점, 해제, 확정, 취소 —
모두 `Idempotency-Key` 헤더를 **필수**로 받는다.

| 상황 | 동작 |
|---|---|
| 같은 키 + 같은 본문 | 저장된 응답을 그대로 재생. 상태는 다시 바뀌지 않는다 |
| 같은 키 + 다른 본문 | 409 `IDEMPOTENCY_KEY_REUSED` |
| 같은 키가 아직 처리 중 | 409 `IDEMPOTENCY_KEY_IN_PROGRESS` |
| 키 누락 | 400 `VALIDATION_FAILED` |

**같은 키로 다른 본문이 오면 조용히 통과시키지 않는다.** 키 재사용은 클라이언트 버그이며,
덮어쓰거나 무시하면 좌석이 잘못 잡힌 채로 넘어간다.

요청 해시에는 **HTTP 메서드와 경로를 포함한다.** 그래야 같은 키를 다른 엔드포인트에
재사용한 경우도 걸린다.

`idempotency_record`는 24시간 보관 후 정리한다. 홀드 TTL(기본 5분)보다 충분히 길어
사용자가 화면을 붙들고 있는 동안의 재시도를 모두 덮는다.

### 6.1 클라이언트가 지켜야 할 것

**네트워크 재시도에서 키를 새로 만들지 않는다.** 응답을 못 받아 재시도할 때 키를 새로
만들면 멱등성이 사라져 좌석이 두 번 잡힌다. 키는 "사용자가 버튼을 누른 행위" 하나에
대응하고, 그 행위의 모든 재전송은 같은 키를 쓴다. 사용자가 실패를 보고 다시 누른
것이라면 그때 새 키를 만든다.

`DELETE /api/holds/{holdId}`와 취소는 그 자체로도 멱등하게 설계했다. 이미 해제된
홀드에 다시 호출하면 204, 이미 취소된 예약에 다시 호출하면 200과 기존 결과가 나간다.
**재시도가 실패로 보이지 않아야 하기 때문이다.**

## 7. 범위 밖

`design-spec.md` 4.3절과 담당 구분에 따라 이 계약에 넣지 않은 것들이다.

| 항목 | 사유 |
|---|---|
| 결제 요청·콜백 엔드포인트 | Mock PG는 박태준 담당이고 인터페이스는 별도 작업이다. 실제 PG 연동은 4.3 제외 항목 |
| QR 티켓 발급·검표 엔드포인트 | REQ-06·REQ-07에 해당하지만 4개월차 작업이며 별도 계약으로 정한다 |
| 알림 발송 엔드포인트 | Outbox는 서버 내부 워커이며 외부 API가 아니다 |
| 관리자 회차·좌석배치 등록 | 최소 관리자 화면은 4.1에 있으나 예약 흐름 계약의 일부가 아니다 |
| 인증·회원 관리 | 요구사항 추적표에 없다. `X-User-Id` 헤더로 대신한다 (화면은 `?userId=` — `scope-m4.md` 6절) |
| 대기열 | 4.2 "여유가 되면" 항목 |

`Reservation` 스키마에 `PENDING_PAYMENT` 상태와 `totalAmount` 필드는 자리만 잡아
두었다. `design-spec.md` 3.3의 상태 전이에 있는 값이라 열거형에서 빼면 나중에 계약을
고쳐야 하기 때문이다. **현재 계약에서 확정은 `HELD → CONFIRMED` 전이이고
`totalAmount`는 0이다.**

## 8. 미결 — 결정이 필요한 항목

착수 전에 정하지 못했고, 추측으로 채우지 않은 것들이다.

### 8.1 ~~k6 시나리오에 폴링을 포함할 것인가~~ — 결정됨: 넣지 않는다

3초 폴링을 부하 시나리오에 넣으면 좌석 조회 부하가 선점·확정 부하와 섞이고, 넣지
않으면 실제 사용 환경과 달라진다 — 어느 쪽이든 보고서에 명시해야 할 문제였다.

**넣지 않기로 정했고, M3의 60회를 전부 그 조건에서 쟀다.** 요청 종류가 둘 이상이
되면 p95와 TPS가 "홀드+확정의 성능"이 아니라 혼합 워크로드의 성능이 되어, 전략
간 비교에서 무엇이 달라졌는지 가려낼 수 없다. 7.1이 지표마다 출처를 못박은 것과
같은 이유다.

**대신 제약으로 명시한다.** 측정값은 폴링 부하가 없는 조건의 것이며, 실사용에서는
좌석맵 폴링이 조회 부하를 추가한다. 폴링 경로는 `ETag`/304로 대부분 빈 응답이
되도록 설계했지만(5.2) 그 효과는 이번 측정에 포함되지 않았다.
`load-test/scenarios/reservation.js` 머리말에 같은 내용을 적어 두었다.

### 8.2 요금 정책 — 미정

요구사항 추적표에 요금·결제 금액 항목이 없다. `totalAmount`는 Mock PG 인터페이스를
정할 때 함께 확정한다.

## 9. 검증

`docs/openapi.yaml`은 아래로 검증했다.

| 도구 | 결과 |
|---|---|
| `js-yaml` (YAML 파싱) | 통과 |
| `@redocly/cli lint` (OpenAPI 3.1 규칙) | 통과 — 오류 0, 경고 1 |

남은 경고 1건은 `servers[0].url`이 `localhost`를 가리킨다는 것이다. 이 프로젝트의 측정
주력 환경이 로컬 Docker Compose이므로(`docs/infra-decision.md`) 의도된 값이며 수정하지
않는다.

인증 스킴이 정의되지 않았다는 지적은 최상위에 `security: []`를 명시해 해소했다.
"인증을 빠뜨린 것"이 아니라 **"인증 요구사항이 없다"**는 선언이다.
