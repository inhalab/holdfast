# M3 결론 — 다섯 전략 측정 종합

락 전략 5종을 같은 하네스로 측정했다. 전략당 3회 × 3경합도 + 세션마다 `none`
고경합 대조군 3회, 총 60회.

**진술마다 뒷받침하는 데이터를 붙이고, 뒷받침되지 않는 것은 조건을 달았다.**

## 0. 한 문단 요약

락이 없으면 경합이 있을 때 깨진다. 락을 거는 방식은 넷이 서로 다르지만 결과는
모두 초과 확정 0이다. **앱 락이 바꾼 것은 경합이 드러나는 방식이지 정합성이
아니며, 정합성의 최종 책임은 DB 제약과 조건부 UPDATE가 진다.** 성능은 전략을
구분하지 못했는데, 이 응용의 임계 구역이 서브밀리초이기 때문이다 — 그것은 결함이
아니라 홀드·확정을 분리한 설계의 결과다.

## 1. 최종 비교 — 고경합 (10석 / 500 VU)

3회 중앙값. 전체 표는 `concurrency-spec.md` 7.6에 경합도별로 있다.

| 전략 | 초과 확정 (3회) | 초과 홀드 | p95 | 같은 세션 `none` | 비율 | 락 포기 | 재시도 | 제약 위반 |
|---|---|---|---|---|---|---|---|---|
| **none** | **5 · 4 · 3** ✗ | 0 | 40ms | — | — | — | — | — |
| pessimistic | 0 · 0 · 0 ✓ | 0 | 32ms | 41ms | 0.78 | 0.00% | — | **0** |
| optimistic | 0 · 0 · 0 ✓ | 0 | 41ms | 33ms | 1.25 | 0.06% | **102** | **0** |
| unique | 0 · 0 · 0 ✓ | 0 | 35ms | 20ms | 1.79 | — | — | **11** |
| redis | 0 · 0 · 0 ✓ | 0 | 18ms | 18ms | **1.01** | 0.00% | — | **0** ※ |

측정 무결성: 60회 전부 5xx 0건 · 미분류 0건. 폐기한 실행 세 벌은
[`discarded-measurements.md`](discarded-measurements.md)에 있다.

**데드락 회피(5.1)도 다섯 전략 전부 0건이다**(7.2.1). 요청당 3석을 무작위 순서로
보내 서버의 좌석 ID 정렬이 실제로 도는지 시험했고, `pg_stat_database.deadlocks`가
다섯 실행 내내 움직이지 않았다. **다만 같은 0이 전략마다 무게가 다르다** —
`pessimistic`은 `FOR UPDATE`로 읽는 시점부터 락을 쥐어 창이 가장 넓고, `redis`는
분산락과 DB 행 락 두 영역을 함께 시험한다(그쪽 순환 대기는 데드락이 아니라 락
포기로 나타나며 그 값도 0이었다). 나머지 셋은 앱 락이 없어 창이 좁지만, 여러
좌석에 쓰는 암묵적 행 락은 그대로 있으므로 공허한 0은 아니다.

## 2. 진술별 검증

### 2.1 "락이 없으면 경합이 있을 때 깨진다. 경합이 없으면 안 깨진다"

**뒷받침된다.** `none`의 초과 확정은 **경합의 함수**다.

| 경합도 | 좌석 | `none` 초과 확정 (3회) |
|---|---|---|
| 저경합 | 1000석 / 100 VU | **0 · 0 · 0** |
| 고경합 | 10석 / 500 VU | **5 · 4 · 3** |
| 극단 | 1석 / 200 VU | **1 · 1 · 1** |

저경합에서 0인 것은 결함이 사라져서가 아니라 **1000석에 100 VU면 같은 좌석을
동시에 노릴 일이 거의 없기 때문**이다. 지속 경합 시나리오에서는 좌석 1석에
120초 동안 **점유 구간 중첩 17,269건**이 나왔다(7.2.2).

**저경합의 초기 관측값(4·2·2)은 측정 절차의 결함이었다.** 재초기화 아티팩트로
판정해 절차를 고치고 다시 쟀다 — 그 경위가
[`reseed-artifact-investigation.md`](reseed-artifact-investigation.md)에 있다.

### 2.2 "다섯 중 넷은 초과 확정 0. 방식은 다르지만 결과는 같다"

**뒷받침된다.** 네 전략 × 3경합도 × 3회 = **36회 전부 V-1 0 · V-2 0 · V-4 0**이다.

| 전략 | 배타성을 보장하는 것 |
|---|---|
| pessimistic | 행 락 (`SELECT ... FOR UPDATE`) |
| optimistic | `version` 조건부 UPDATE + 재시도 |
| unique | U-2 부분 유니크 인덱스 |
| redis | 분산락 + U-2 계층 방어 |

### 2.3 "앱 락이 바꾼 것은 경합이 드러나는 방식이지 정합성이 아니다"

**뒷받침된다. `unique`가 결정적이다** — 앱 레벨 락을 **전혀 쓰지 않는데** 9회
전부 초과 확정 0이다.

같은 사건(동시에 같은 좌석을 노린 요청)이 전략마다 다른 자리에 나타난다.

| 전략 | 그 사건이 나타나는 곳 | 고경합 3회 |
|---|---|---|
| pessimistic | 행 락 대기 → 대부분 즉시 거절 | 락 포기 0 |
| optimistic | version 충돌 → 재시도 | **재시도 102 · 소진 34** |
| unique | INSERT 충돌 → 제약 위반 | **제약 위반 11** |
| redis | 분산락 대기 | 락 포기 0 |

**`unique`의 제약 위반 11건이 다른 전략에서 앱 락이 흡수하던 숫자다.**

### 2.4 "정합성의 최종 책임은 DB 제약과 조건부 UPDATE에 있다"

**뒷받침된다. 두 장치가 5개 전략 공통으로 깔려 있다.**

| 장치 | 막는 것 | 예외 |
|---|---|---|
| U-2 부분 유니크 인덱스 | 같은 좌석에 활성 홀드 둘 | `none`만 제거(2.1) |
| `confirmIfStillHeld` 조건부 UPDATE | 같은 좌석의 이중 확정 | `none`만 순진한 SELECT-후-UPDATE |

**가장 강한 증거는 `redis`의 리스 만료 실험이다.** 정상 조건에서는 락이 새지
않아 명제가 드러나지 않으므로, 리스를 1ms로 낮춰 획득 직후 만료시켰다.

```
[redis 리스만료] 30스레드 → 제약 위반 9건 · 초과 홀드 0건 · 활성 홀드 1건
```

**락은 뚫렸는데 좌석은 한 명에게만 갔다.** 4.5.1의 "분산락은 성능 최적화이지
정합성 보장이 아니다"가 그대로 관측된 것이다.

### 2.5 "성능은 전략을 구분하지 못한다"

**뒷받침된다. 단, 근거는 절댓값이 아니라 대조군이다.**

같은 `none` 고경합을 다섯 세션에서 쟀다 — **41 · 38 · 33 · 20 · 18ms.** 두 배 넘게
흔들린다. 그리고 **다섯 전략의 p95가 전부 그 폭 안에 들어간다**(18 · 32 · 35 ·
40 · 41ms).

**`redis`가 이 판정의 가장 강한 확증이다.** 절댓값 18ms로 다섯 중 가장 낮아
"분산락이 제일 빠르다"로 읽힐 뻔했는데, **같은 세션 대조군도 17.98ms였다.**
비율 1.01 — 빨랐던 것은 전략이 아니라 그 세션이다.

**대조군이 없었다면 정반대 결론을 적었을 것이다.** `redis` 18ms와
`pessimistic` 32ms를 나란히 놓으면 "분산락이 1.8배 빠르다"가 된다.

경합도 3단계에서 관측된 p95 차이도 이미 커넥션 대기열로 설명됐다
([`p95-inversion-investigation.md`](p95-inversion-investigation.md)).

**이 결론은 반대를 예상하고 재서 얻은 것이다.** 착수 시점에 `concurrency-spec`
7.2는 "낙관적 락은 저경합에서 가장 빠르고 고경합에서 재시도가 폭발하며, 비관적
락은 반대다 — 이 **교차점**을 숫자로 잡으면 '경합도 N 이상에서 뒤집힌다'고 말할
수 있다"고 적었다. **교차점은 없었다.** 뒤집힐 순위 자체가 세션 간 변동 안에
들어가기 때문이다. 사전 가설과 회수 근거는
[`discarded-measurements.md`](discarded-measurements.md) A절에 남겼다 —
**예상을 적어 두지 않았다면 이 결론은 "처음부터 그럴 줄 알았다"로밖에 읽히지
않는다.**

### 2.6 "임계 구역이 서브밀리초이기 때문이며, 홀드·확정 분리 설계의 결과다"

**앞부분은 뒷받침된다. 뒷부분은 해석이므로 그렇게 표시한다.**

**측정된 사실**은 이렇다.

| 관측 | 값 |
|---|---|
| `pessimistic`의 커넥션 점유 (지속 경합) | 5.340ms |
| `none`의 커넥션 점유 (같은 조건, 락 없음) | 5.330ms |
| **`FOR UPDATE` 획득과 락 대기가 더한 점유** | **0.010ms (0.19%)** |
| 락 포기율 (전 전략·전 시나리오) | 0에 수렴 |

**락을 쥔 채 하는 일이 거의 없다.** 지속 경합 시나리오를 따로 만들어 락 대기를
키우려 했으나 실패했고, 그 조사가
[`sustained-lock-wait-investigation.md`](sustained-lock-wait-investigation.md)다.

**"홀드·확정 분리 설계의 결과"는 인과 해석이다.** 결제가 임계 구역 안에 있는
설계와 비교 측정한 것이 아니므로 실험으로 증명하지는 않았다. 다만 홀드
트랜잭션이 인덱스를 탄 몇 개의 문장뿐이고 결제가 그 밖에 있다는 것은 설계
문서(3절 홀드 정책)와 코드에서 확인되며, 그것이 임계 구역이 짧은 직접적인
이유다. **반증 가능한 형태로 적으면** — 결제를 임계 구역 안으로 옮기면 락 대기가
p95를 지배하기 시작할 것이다. 검증하지 않았다.

## 3. 그래서 무엇을 고를 것인가

성능이 전략을 구분하지 못하므로 **선택 기준은 정합성 보장 방식과 운영 특성**이다.

| 전략 | 강점 | 약점 | 적합한 곳 |
|---|---|---|---|
| pessimistic | 단순하고 예측 가능. 실패 모드가 명확(대기 후 포기) | 대기 중 DB 커넥션을 점유 | 임계 구역이 짧고 단일 DB인 경우 — **이 프로젝트의 기본값** |
| optimistic | 락을 잡지 않아 대기 없음 | 경합이 커지면 재시도가 폭발. 상한 조정이 필요 | 충돌이 드문 경우 |
| unique | 앱 코드가 가장 단순. 방어가 DB 한 곳 | 실패가 예외로 오고, 제약 이름에 의존 | 앱이 여러 개이거나 앱을 신뢰할 수 없을 때 |
| redis | DB 밖에서 경합을 흡수 | **정합성을 보장하지 않는다.** 운영 요소가 하나 늘어난다 | DB 부하를 덜어야 할 만큼 경합이 클 때 |

**어느 것을 고르든 U-2와 조건부 UPDATE는 남긴다.** 그것이 실제로 정합성을
지키고 있다는 것이 이 측정의 결론이다.

## 4. 측정 방법에서 배운 것

세 번의 폐기와 두 번의 조사가 프로토콜을 바꿨다. 상세는
[`discarded-measurements.md`](discarded-measurements.md)에 있고, 한 줄로 줄이면
이렇다.

> **숫자 하나만 보고 판정하지 않는다. 모든 판정에는 어긋나면 드러나는 짝이
> 있어야 한다.**

오류율에는 앱 로그가, 측정 구간 성공 건수에는 DB 재고 상태가, V-1에는 경합도별
추세가, **p95에는 같은 세션 대조군이** 짝이었다. 마지막 것이 이번 M3에서 가장
많은 오독을 막았다.

## 5. 남은 것 — 그리고 자른 것

**데드락 검증(7.2.1)은 M3에서 마무리했다.** 위 1절 참조.

**지속 경합 시나리오(7.2.2)를 나머지 세 전략으로 돌리지 않고 자른다.**

그 시나리오는 원래 7.5(분산락이 대기 중 커넥션을 점유하지 않아 p95에서 앞선다)를
시험하려고 만들었는데, **7.5는 이 조건에서 검증 불가로 판정됐다** — 응용의 임계
구역이 서브밀리초라 락 대기가 사실상 발생하지 않는다
([`sustained-lock-wait-investigation.md`](sustained-lock-wait-investigation.md)).
그래서 시나리오를 4.5.1 검증용으로 재배치했고(7.5.1), 세 전략을 더 돌려 얻을 수
있는 것은 **4.5.1 한 건뿐**이다.

**그 한 건은 이미 실증됐다.** 리스를 1ms로 낮춘 단위 테스트에서 제약 위반 9건 ·
초과 홀드 0건이 나왔다 — 락은 샜고 DB 제약이 받아냈다. 부하로 다시 재도
정상 조건에서는 "관측하지 못했다"가 나올 뿐이고, 그것은 7.5.1이 미리 밝힌 대로
반증이 아니다. **얻는 것이 없는 실행은 하지 않는다.**

**Outbox 확장 측정(7.8)이 이 절의 결론 하나를 뒤집었다.** 세션
`20260903-2038`에서 고경합 5전략 15회를 다시 쟀고, 오류율 0% · 미분류 0건으로
전 회차가 유효하다. **정합성 쪽은 그대로다** — `none`만 V-1 4·2·3으로 깨지고
나머지 넷은 0이며, `unique`의 제약 위반 50건은 전부
`ux_seat_hold_active`(U-2)로 찍혀 4.4가 말한 대로였다. **바뀐 것은 이
2.5절이다.** 확정 트랜잭션에 알림 Outbox의 INSERT 한 문장이 늘자
`pessimistic`이 같은 세션 `none` 대조군 대비 **커넥션 점유 1.200배 · p95
1.271배 · p99 55ms(다른 넷은 21~23ms)** 로 분리됐다. **M3에서 0.010ms였던
점유 차가 0.698ms — 70배다.** `redis` 1.064, `optimistic` 1.013, `unique`
1.014로 앱 락을 쓰는 둘이 앞서고 락 없는 둘은 대조군에 붙어, 서로 독립인 두
지표(점유·p95)가 같은 순서를 냈다. **7.7.1이 예고한 "더 긴 임계 구역을 갖는
응용에서는 결론이 달라질 수 있다"가 맞았고, M3에서 차이가 보이지 않은 것은
전략이 같아서가 아니라 임계 구역이 너무 짧아 잡음에 묻혔기 때문이다.** 다만
이번 세션은 대조군을 맨 앞에서 한 번만 쟀으므로(M3는 전략마다 붙였다) **"이
조건에서 그렇게 보인다"까지가 정확한 표현이다.** 전말은 `concurrency-spec`
7.8.2에 있다.

**여기까지 온 경위는 이렇다.** M4에서
알림 Outbox가 확정 트랜잭션 안에서 `outbox` 행을 INSERT하게 되어 CS-2의 임계
구역이 문장 하나만큼 길어졌고, 그것이 위 2.5·2.6의 근거("임계 구역이
서브밀리초라 락 대기가 응답시간을 지배할 구간이 없다")를 흔드는지 보려고 고경합
5전략 15회를 계획했다(7.8). **1차 시도는 폐기했다** — `nginx`가 측정 1시간
45분 전에 종료돼 있어 15회 전부 성공 0건 · 오류율 100%로 끝났고, 좌석은 측정
뒤에도 10석 전부 `AVAILABLE`이었다
([`discarded-measurements.md`](discarded-measurements.md) 4번). 그 사이 사전
점검을 프로토콜에 넣었고(7.4.0), 2차 시도가 위 문단의 결과다.

**AWS 환경 재측정도 자른다.** `concurrency-spec` 7.3은 "3개월차 AWS 환경에서
k6를 별도 인스턴스로 분리해 다시 잰다"고 적었으나, 27회 두 시간 반을 들여
얻을 것이 **p95 절댓값의 소폭 개선뿐**이고 이 절의 결론("성능은 전략을 구분하지
