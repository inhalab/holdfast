# 지속 경합 조사 — 7.5는 이 조건에서 검증할 수 없다

7.2.2 지속 경합 시나리오는 **7.5 사전 가설을 시험할 조건을 만들려고** 설계했다.
그 목적은 달성되지 않았다. 왜 실패했는지, 무엇을 오독했다가 어떻게 정정했는지,
그리고 이 실패가 M3 전체 결론에 무엇을 뜻하는지 남긴다.

`p95-inversion-investigation.md`와 같은 성격의 문서다. **검증 실패도 결과다.**

## 0. 요약

| 질문 | 답 |
|---|---|
| 지속 경합이 락 대기를 만들었는가 | **아니다.** 추가 커넥션 점유 0.010ms |
| 홀드 p95 240ms는 무엇인가 | 락 대기가 아니라 **애플리케이션 대기열** |
| 7.5는 검증됐는가 | **검증 불가(B)** — 가설이 전제한 조건이 성립하지 않았다 |
| 7.5는 반증됐는가 | **아니다.** 조건이 없었으므로 예측을 시험한 적이 없다 |

## 1. 측정 — `none`과 `pessimistic`, 같은 설정

좌석 1석 / VU 500 / `sleep` 50ms / 120초 (7.2.2 확정 설정), 전략당 3회.

| 지표 (3회 중앙값) | `none` | `pessimistic` |
|---|---|---|
| **홀드 p95** | **239.80ms** | **240.94ms** |
| 홀드 p99 | 341.94ms | 329.87ms |
| 홀드 평균 | 99.08ms | 95.54ms |
| 홀드 요청 | 393,836 | 410,128 |
| **홀드 성공** | **26,778** | **2,387** |
| 409율 | 93.40% | 99.42% |
| TPS · 반복/s | 3,392 · 3,223 | 3,428 · 3,293 |
| 락 포기 · 5xx · 미분류 | 0 · 0 · 0 | 0 · 0 · 0 |
| 회수 성공률 · L-1 · L-2 | 100% · 0 · 0 | 100% · 0 · 0 |
| **V-6 점유 구간 중첩** | **17,269** | **0** |

커넥션 풀 지표는 전략 전환 시 앱을 재기동해 카운터가 지워지므로, **같은 세션에서
두 전략을 1회씩 다시 돌려 0에서 시작한 값**으로 잡았다(7.4.2의 대조군 규칙).

| 전략 | **커넥션 점유(`usage`)** | 획득 대기(`acquire`) | 획득 횟수 |
|---|---|---|---|
| `none` | **5.330ms** | 23.184ms | 1,484,166 |
| `pessimistic` | **5.340ms** | 22.400ms | 1,497,789 |

보강 측정 회차의 나머지 값도 3회 측정과 일치한다 — `none` 홀드 p95 243.52ms ·
V-6 16,403 · 회전 16,558, `pessimistic` 216.80ms · V-6 0 · 회전 1,560, 양쪽 모두
락 포기 0 · 5xx 0 · 회수 100%.

## 2. 홀드 p95 240ms는 락 대기가 아니다

**결정적 증거는 `none`이다. 락이 아예 없는데 p95가 같다**(239.80 vs 240.94,
0.5% 차이). 240ms가 락 대기라면 `none`은 훨씬 빨라야 한다.

정체는 애플리케이션 대기열이다.

- 반복 3,230/s × 500 VU → 반복 주기 154.8ms. `sleep` 50ms를 빼면 요청 105ms이고
  홀드 평균 99ms와 맞는다.
- Little의 법칙: 동시 처리 중인 요청 = 3,400 × 0.099 ≈ **337건**. Tomcat 스레드
  400개(200 × 앱 2대)에 근접한다.
- 여기에 k6가 **같은 머신에서** 3,400 req/s를 만들며 CPU를 나눠 쓴다(7.3 미충족).

**"일이 10배 다르다"도 절대량으로는 작다.** 홀드 성공 차이 24,391건은 120초에
걸쳐 203/s이고 전체 3,400 req/s의 **6%**다. 나머지 94%는 두 전략이 동일한 거절
경로를 탄다. 경합도 3단계에서 작업량 가설을 기각했을 때와 같은 구조다
(`p95-inversion-investigation.md` 1절).

## 3. 락 대기 자체가 없었다

**커넥션 점유가 답을 준다.** `none`은 락이 없으므로 5.330ms가 이 트랜잭션의
작업 시간 하한이다. `pessimistic`은 5.340ms — **`FOR UPDATE` 획득과 락 대기를
합친 추가 점유가 0.010ms(0.19%)** 다. 획득 대기는 오히려 0.78ms *낮다*.

왜 대기가 없는가. **행 락은 커밋 시점에 풀리기 때문이다.**

- 좌석 1석의 회전은 1,560~1,700회/120초 = **13~14/s**. 좌석은 사실상 100%
  논리적 `HELD` 상태다.
- 그러나 승자가 **행 락**을 쥐는 것은 홀드 트랜잭션 동안(수 ms)뿐이고, 커밋 후
  해제 요청이 올 때까지 70ms 남짓은 행이 잠겨 있지 않다.
- 그래서 나머지 요청은 기다린 것이 아니라 **`FOR UPDATE`로 잡고 "이미 HELD"를
  보고 즉시 나온다.** 서브밀리초다.

점유율로 계산하면
`ρ ≈ 승자 14/s × 4ms + 거절 3,400/s × 0.2ms ≈ 0.74`, 평균 대기 ≈ 0.6ms —
99ms 응답의 0.6%다. 락 포기 0건이 이를 뒷받침한다.

**도착률도 폐루프에 종속됐다.** `sleep` 50ms인데 응답이 240ms라, 반복 주기
155ms 중 `sleep`은 32%뿐이고 나머지 68%를 서버가 정한다. `sleep`은 더 이상
도착률 손잡이가 아니다.

## 4. 오독과 정정 — `sleep`을 낮췄더니 p95가 올랐다

**7.2.2 보정 단계에서 나는 이렇게 판단했다.**

> `sleep`을 1000ms → 50ms로 줄이자 홀드 p95가 47ms → 236ms가 됐다.
> **응답시간의 대부분이 락 대기이며, 이것이 원래 재려던 값이다.**

**틀렸다.** 그 상승은 도착률이 491/s → 3,484/s로 오르며 생긴 애플리케이션
대기열이었다. 파일럿을 `pessimistic` 하나로만 돌린 것이 오독의 원인이다 —
비교 대상이 없으니 "락이 있는 전략에서 대기가 늘었다"를 "락 대기가 늘었다"로
읽었다.

**`none` 대조군이 정정했다.** 락이 없는 전략을 같은 설정으로 돌리자 239ms가
나왔다. 대기의 출처가 락이 아님이 한 번에 드러났다.

**교훈은 7.4.2가 이미 적어 둔 것과 같다** — 대조군 없이는 어떤 차이도 원인에
귀속시킬 수 없다. 그 규칙을 본 측정에는 적용했으면서 **파일럿에는 적용하지
않은 것이 이번 실수다.** 보정 파일럿에도 대조군을 넣는다.

## 5. 결론 — B(검증 불가). C(반증)가 아니다

**7.5는 이 조건에서 검증할 수 없다.**

> Redis 분산락이 p95에서 비관적 락을 앞설 것이다. Redis가 빨라서가 아니라,
> 락 획득을 트랜잭션 시작 **전에** 수행하면 대기 중 DB 커넥션을 점유하지 않기
> 때문이다.

가설이 전제한 비용은 **"대기하는 동안 커넥션을 쥔다"** 인데, 3절대로 그 대기가
0.010ms다. **`pessimistic`이 가설이 말하는 비용을 지불한 적이 없다.**

**반증이 아닌 이유가 중요하다.** 반증하려면 가설이 전제한 조건에서 예측이
빗나가야 한다. 조건 자체가 성립하지 않았으므로 예측을 시험한 적이 없다.
`redis`가 이 조건에서 이겨도 검증이 아니라고 적었던 것과 **같은 규율의 반대
방향**이다.

### 고칠 방법이 없는가 — A를 기각한 근거

시나리오를 고쳐 락 대기를 만들 수 있는지 검토했다.

| 손잡이 | 한계 |
|---|---|
| 좌석 수 | **1석이 하한이다.** 파일럿에서 3→1석이 유효하지 않음이 이미 확인됐다 |
| 도착률(`sleep`) | **폐루프에 막혔다.** 응답 240ms가 `sleep` 50ms를 압도해 더 낮춰도 도착률이 늘지 않는다 |
| VU 증가 | 대기열만 더 길어진다. 락 점유율은 요청당 0.2ms에 묶여 있다 |
| `lock_timeout` 낮추기 | 7.2.2에서 기각. 포기율은 얻지만 재려던 점유를 함께 잘라낸다 |

**근본 원인은 시나리오가 아니라 응용의 성질이다.** 이 응용의 임계 구역은
서브밀리초다 — 홀드 트랜잭션은 인덱스를 탄 몇 개의 문장이고, 결제는 홀드·확정
분리로 임계 구역 밖에 있다(3절 홀드 정책). **락을 쥔 채 하는 일이 없으므로 락
대기가 응답시간을 지배할 구간이 존재하지 않는다.**

이것은 결함이 아니라 설계의 결과다. 오히려 그 설계가 옳았다는 증거에 가깝다.

## 6. 이 발견은 7.5보다 크다 — M3 결론 구조

**락 대기가 응답시간을 지배할 구간이 없다면, 락 전략 선택이 이 응용의 성능에
미치는 영향 자체가 미미하다.** 지금까지의 측정이 그것을 뒷받침한다.

| 근거 | 값 |
|---|---|
| 지속 경합 홀드 p95 | 239.80 vs 240.94ms — 0.5% |
| 지속 경합 커넥션 점유 | 5.330 vs 5.340ms — 0.19% |
| 경합도 3단계 p95 차이 | 실재했으나 **커넥션 대기열로 설명됐다**(`p95-inversion-investigation.md`) |
| 락 포기율 | 전 시나리오 0에 수렴 |
| **초과 확정(V-1)** | none 2·4·1 / **pessimistic 0·0·0** |
| **점유 중첩(V-6)** | none 17,269 / **pessimistic 0** |

**성능 지표는 노이즈 안에서 겹치고, 정합성 지표는 자릿수로 갈린다.**

그래서 M3의 결론 구조를 바꾼다.

> **"어느 전략이 빠른가"가 아니라 "성능은 대체로 비슷하고, 차이는 정합성 보장
> 방식과 운영 특성에 있다"** 가 M3의 예상 결론이다.

**아직 2/5 전략만 쟀다는 한계는 분명히 둔다.** 남은 셋 중 성능 차이가 나타날 수
있는 후보는 두 가지이며, 둘 다 락 대기가 아니라 **전략 고유의 추가 작업**이다.

- `optimistic` — 재시도는 같은 일을 다시 한다. 응답시간에 직접 더해진다
- `redis` — 락 획득에 네트워크 왕복이 추가된다

**예측을 적어 둔다.** 두 전략에서 p95 차이가 나온다면 그 원인은 락 경합 비용이
아니라 위 두 가지일 것이다. 틀리면 이 문서를 정정한다.

### 남은 세 전략에서 볼 것

p95 순위가 아니다.

| 볼 것 | 왜 |
|---|---|
| **정합성 보장 방식** (앱 락 / 제약 / 재시도) | 성능이 비슷하다면 이것이 선택의 근거다 |
| **제약 위반 카운터 0인가** | 앱 레벨 방어가 실제로 작동했는지의 유일한 증거. `unique`는 0이 아닌 것이 정상 |
| **전략 고유 비용이 어디서 나타나는가** | `optimistic`의 재시도 횟수, `redis`의 락 포기·왕복 |
| **실패 모드** | 무엇이 잘못되면 어떻게 드러나는가. 조용히 틀리는 전략이 가장 나쁘다 |

## 7. 7.5와 4.5.1의 관계 — 시나리오를 재배치한다

지속 경합 시나리오는 7.5 검증에는 실패했지만 **4.5.1 검증에는 유효하다.**

> **4.5.1** 이 락은 정합성을 보장하지 않는다 — 분산락은 성능 최적화이지 정합성
> 보장이 아니다.

이 명제는 락 대기가 필요 없다. 필요한 것은 **좌석 하나를 두고 요청이 끊임없이
겨루는 상태**이고, 그것은 이 시나리오가 실제로 만들어낸다 — `none`이 120초에
17,269건의 점유 중첩을 냈다.

**판정 기준은 제약 위반이다.**

| 결과 | 해석 |
|---|---|
| `redis`에서 **제약 위반(U-2) > 0** | **4.5.1 실증.** 분산락이 샜고 DB 제약이 막았다 |
| `redis`에서 V-6 > 0 | 더 나쁘다. U-2마저 막지 못했다는 뜻이다 |
| 둘 다 0 | **명제의 반증이 아니다.** "이 부하·이 설정에서는 새지 않았다"까지만 말한다 |

**V-6이 아니라 제약 위반이 1차 지표인 이유**는 U-2가 걸려 있기 때문이다.
`redis` 락이 새어 두 요청이 같은 좌석을 홀드하려 하면 두 번째 INSERT가 U-2에
막혀 **제약 위반 카운터가 오르고 V-6은 0으로 남는다.** `none`은 U-2를 지우고
재므로(erd 3.1) 중첩이 V-6에 그대로 드러난다 — **`none`이 대조군인 것이 이
구조 때문이다.**

**둘 다 0일 때 반증이 아닌 이유도 분명히 한다.** Redisson 락이 새는 조건은
락 만료와 GC 정지 같은 것인데, 120초 실행에서 그 조건이 재현된다는 보장이 없다.
"새는 것을 관측하지 못했다"와 "새지 않는다"는 다르다.

## 8. 측정 무결성

3회 측정 6벌과 보강 2벌 모두 다음을 만족한다.

| 점검 | 결과 |
|---|---|
| 5xx·타임아웃 | 0건 |
| 미분류 응답 | 0건 |
| 회수 성공률 | 100% (실패 0건) |
| L-1 잔여 활성 홀드 · L-2 미반환 좌석 | 0 · 0 |
| 본 측정 길이 | 120초 |

회수 누수가 0이므로 재고가 순환에서 빠진 회차는 없다(7.2.2의 폐기 사유).
k6가 앱과 같은 머신에서 도는 7.3 미충족 사항은 `m2-none-baseline.md` 2.1절과
동일하게 적용되며, **이 시나리오에서는 그 영향이 더 크다** — 3,400 req/s를
생성하느라 k6가 쓰는 CPU가 곧 앱의 대기열이 된다.
