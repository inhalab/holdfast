# 협업 규칙

## 기본 흐름

`main`은 직접 push가 막혀 있다. 모든 변경은 브랜치를 만들어 PR로 올린다.

```bash
git switch main && git pull          # 최신화
git switch -c infra/ecs-setup        # 브랜치 생성
# 작업, 커밋
git push -u origin HEAD              # 현재 브랜치명 그대로 푸시
gh pr create --fill                  # 커밋 메시지로 PR 생성
```

CI를 확인하고 머지한다.

```bash
gh pr checks --watch                 # 초록불 대기
gh pr merge --squash --delete-branch # 머지 + 브랜치 삭제
git switch main && git pull          # 로컬 최신화
```

**승인은 필요 없다.** CI만 통과하면 혼자 머지할 수 있다. 2인 프로젝트에서 승인을 강제하면 서로 대기하다 멈추기 때문이다. 다만 상대가 봐야 할 변경이면 리뷰어를 지정한다.

## 브랜치 이름

| 접두사 | 용도 | 예 |
|---|---|---|
| `feat/` | 기능 추가 | `feat/seat-hold` |
| `fix/` | 버그 수정 | `fix/expire-race` |
| `infra/` | 인프라, 배포, CI | `infra/ecs-setup` |
| `docs/` | 문서 | `docs/concurrency-design` |
| `chore/` | 설정, 잡무 | `chore/update-codeowners` |

## 커밋 메시지

```
<type>: <한 줄 요약>
```

type은 브랜치 접두사와 같은 어휘를 쓴다. 한국어로 쓰되 명령형보다 서술형이 읽기 편하다.

```
feat: 좌석 선점 API 추가
fix: 홀드 만료와 확정의 경합 처리
docs: 동시성 설계서 추가
```

머지는 squash로만 하므로 작업 중 커밋은 자유롭게 쪼개도 된다. main 히스토리에는 PR 하나가 커밋 하나로 남는다.

## PR 규칙

템플릿(`.github/pull_request_template.md`)의 세 항목을 채운다.

```markdown
## 무엇을
## 왜
## 확인 방법

관련 이슈: #
```

관련 이슈 번호를 적으면 이슈 페이지에서 역참조가 보인다. `Closes #12`라고 쓰면 머지 시 이슈가 자동으로 닫힌다.

## CODEOWNERS

`.github/CODEOWNERS`에 정의된 경로를 건드리면 담당자가 자동으로 리뷰어에 붙는다. 승인 강제는 아니고 알림 역할이다. 접근 권한이 아니라 리뷰 책임의 구분이므로 상대 영역도 필요하면 손댄다.

### 리뷰는 필수가 아니다 — 그래서 언제 기다릴지를 적어 둔다

**사실부터.** `main`에 **브랜치 보호가 없다.** CODEOWNERS는 리뷰어를 붙이지만
**요구로 걸려 있지 않다.** 승인 0건이어도 머지된다.

```bash
gh api repos/:owner/:repo/branches/main/protection
#   404 Branch not protected          ← 필수 리뷰가 없다

gh pr view <N> --json mergeStateStatus,reviewDecision
#   CLEAN   + reviewDecision 비어 있음 ← 리뷰 없이 머지 가능
#   BLOCKED                            ← 보통 CI 가 안 끝난 것이다
```

**`BLOCKED`은 리뷰가 아니라 CI다.** 승인이 없어서 막히는 일은 이 저장소에
없다.

#### 그럼에도 기다리는 기준 — 경로로 정한다

**「중요해 보이면 받는다」로 두면 그때그때 달라진다.** 판단이 아니라 **디프에서
확인되는 것**으로 적는다.

| 이 경로가 바뀌면 **기다린다** | 왜 |
|---|---|
| **`api/src/`** (`main`·`test` 둘 다) | 동작과 **그 동작을 지키는 장치**가 여기 있다 |
| **CODEOWNERS 밖 경로** (`holdfast` 같은 루트 파일) | 붙을 담당자가 없어 **아무도 안 본다** |
| **`load-test/scripts/` · `load-test/sql/`** | 측정 프로토콜이다. 바뀌면 이미 잰 값의 뜻이 바뀐다 |

**나머지(문서만)는 안 기다려도 된다.** 기다려서 얻는 것이 없다.

> **`api/src/test/`를 뺄 뻔했다.** *"동작이 바뀌는 것만"*으로 좁히면 테스트는
> 빠지는데, **`#210`에서 F3ZLoV가 잡은 것이 정확히 테스트였다** — 취소가 전부
> 실패해도 초록이 되는 **헛통과**였다. **아무 일도 안 하면서 통과로 보이는 것**은
> `#222`가 모은 부류이고, 그것을 스스로 알아차리기 가장 어렵다.

> **「필수가 아니다」가 「안 받아도 된다」는 아니다.** `#221`은 위 셋 중 둘에
> 걸렸고(`api/src/`, `load-test/`), 그 안에서 판단이 **세 번 뒤집혔다** — 락
> 순서를 바꿨다가 되돌리고, 게이트 위치 서술을 정정하고, 데드락 0의 근거를
> 갈았다. **전부 혼자 검증한 것이다.**

#### 리뷰가 잡는 것은 결함만이 아니다 — 근거를 단단하게 만든다

**`#221`의 실측 사례다.** 그 PR은 취소가 할당량을 여러 번 깎던 것을
`releaseByHoldId`의 `rowsAffected`로 막는 변경이었다. **왜 그 수를 써도 되는지**를
만든 쪽도 읽은 쪽도 *"`SeatHoldService#release`가 이미 그렇게 한다"* 까지만
적었다.

**리뷰는 스키마까지 내려갔다.**

> `seat_hold`는 **좌석당 한 행**이고 `hold_id`가 그룹 키다
> (`V1__init_schema.sql`). 그래서 `releaseByHoldId`의 `rowsAffected`가 **곧
> 좌석 수**이고, `seatIds.size()` 자리에 그대로 들어간다.

**코드는 바뀌지 않았다. 그 고침이 왜 맞는지가 바뀌었다** — *"저쪽도 그렇게 하니까"*
에서 *"스키마가 그렇게 생겼으니까"*로.

**그래서 리뷰는 결함이 없을 때도 값을 한다.** 필수가 아닌데도 위 기준으로 받기로
한 판단을 이것이 받친다.

## 이슈와 보드

작업은 [로드맵 보드](https://github.com/orgs/inhalab/projects/1)의 **Priority 숫자 순서**대로 진행한다. Priority `0`은 해당 마일스톤의 진행 순서를 담은 트래킹 이슈다.

> **한때 *"담당자별로 그룹이 나뉘어 있고 각자 1부터 시작한다"*라고 적혀 있었다.**
> 지금은 **두 사람이 한 줄에 섞여 있는 전역 순서**다 — 열린 일곱이
> `52`~`58`로 담당자와 무관하게 이어진다. 축이 갈려 병렬로 돌아도 **무엇을
> 먼저 하느냐는 하나로 읽혀야 하기 때문**이고, `#42`와 `#215`처럼 담당자가
> 다른 두 항목 사이에 선행 관계가 생기면 담당자별 번호로는 그것을 적을 수 없다.

새 작업이 생기면 이슈를 먼저 만들고 보드에 올린다.

```bash
gh issue create -R inhalab/holdfast \
  -t "제목" -l "area:api" -m "M1 설계 및 환경 구축" -a Asirante -b "본문"
```

라벨은 `area:api` / `area:infra` / `area:docs`, `type:feat` / `type:fix` / `type:chore`, 그리고 동시성 관련이면 `concurrency`를 붙인다.

### Status 열은 `In Progress` 로만 값을 낸다

**`Todo`와 `Done`은 이슈의 열림·닫힘을 그대로 복제한 것이다.** 닫으면 GitHub
기본 워크플로가 `Done`을 박고, 그 외에는 `Todo`다. **그 둘만 있으면 이 열은
정보가 0이고**, 같은 사실을 두 곳에서 지키는 형태가 된다(`erd.md` 4절).

**그래서 열이 값을 내는 자리는 `In Progress` 하나뿐이고, 조건을 기계적으로
못박는다.**

> **`In Progress` = 그 이슈의 PR이 하나 이상 머지됐는데 이슈가 아직 열려 있는 것.**

**판단이 들어가지 않아야 안 낡는다.** *"진행 중인 느낌"*으로 두면 아무도
갱신하지 않고, 이 저장소는 그 형태로 한 번 당했다 — `#127`의 테스트 합계가
*"아무도 실행하지 않는 숫자는 조용히 틀린다"*였다.

**왜 필요한가.** `#42`가 `#207`·`#211`로 Terraform·apply·검증까지 끝났는데
이슈는 열려 있다. **`Todo`로 두면 「아직 시작 안 했다」로 읽히고**, 4주차 발표
자료가 같은 항목을 **90%**로 싣는다. **저장소가 PUBLIC이고 발표 자료가 이슈
번호로 이곳을 가리키므로**(`submissions/README.md` 규약) 둘이 맞부딪힌다.

**`In Progress`가 하나도 없는 상태가 정상일 수 있다.** 값을 채우려고 억지로
옮기지 않는다 — 위 조건에 맞는 것이 없으면 없는 것이다.

## 문서를 코드와 함께 갱신한다

**M4 착수 전 문서 감사에서 사실 오류 10건·문서 간 충돌 7건·폐기된 전제 9건이
나왔다.** 하나하나는 사소했지만 한 가지 종류로 쌓였다 — **판단이 바뀔 때 코드는
고치고 문서는 두었다.** 아래 아홉 중 1~6은 그 감사에서 뽑았고, 7은 감사 전에 한
번 겪은 것이 다시 나서 세웠다. 9는 그 뒤에 같은 종류로 한 번 더 겪고 세웠다.
**8만 성격이 다르다** — 문서가 아니라 PR 운영 규칙인데, 같은 번호로 참조할 수
있게 여기 둔다.

### 1. 구현이 문서와 갈리면 같은 PR에서 문서도 고친다

코드 주석에 "문서 N절은 X라고 하지만 여기서는 Y"라고 쓰는 것은 이탈을
**기록한** 것이지 **해소한** 것이 아니다. 그 절에 갱신 블록을 함께 단다.

`erd.md` 4.1의 `redis` 행이 그 형태다("이 표가 처음 적은 것은 …이었으나 구현은
그렇게 하지 않았다"). 같은 표의 `optimistic` 행은 그러지 못해, **구현과 정반대인
서술이 세 달 남아 있었다.**

#### PR 본문도 여기 들어간다 — 코멘트로 정정하지 않는다

**PR 본문은 그 변경이 왜 맞는지의 기록이고, 나중에 누군가 그것을 근거로 다른
판단을 한다.** 그러므로 **본문이 코드와 갈리면 본문을 고친다** — 아래에 정정
코멘트를 다는 것은 이탈을 **기록**한 것이지 **해소**한 것이 아니다.

**코멘트는 스크롤에 묻히고, 나중에 이 PR을 근거로 찾는 사람은 본문을 본다.**

> **`#221`에서 리뷰 한 바퀴를 이것 때문에 돌았다.** 본문이 *"게이트를 좌석
> **앞으로** 옮겼다"*로 적혀 있었는데 그 뒤 락 순서를 되돌리며 **본문을 안
> 고쳤다.** 정정 코멘트는 달았지만 본문은 그대로였다.
>
> **리뷰가 잡은 위험이 정확히 「나중에」였다** — *"이 PR을 근거로 C-2를
> 「해결됨」으로 옮기면 그때 틀린다."* **본문이 문서라는 증거다.**

### 2. 측정을 반영하는 PR은 표만이 아니라 그 표가 무효화한 전제까지 범위에 넣는다

**측정 반영 PR 체크리스트** — 이번에 얻은 숫자가 아래 셋 중 무엇을 뒤집었는지
확인하고, 뒤집었으면 같은 PR에서 처리한다.

- [ ] **사전 가설** — 이 숫자가 가설을 확증했나, 반증했나, 검증 불가로 만들었나?
      (`concurrency-spec.md` 7.5·7.7)
- [ ] **지표 표의 목표 열** — "0 기대" 같은 기대값이 이 전략에도 맞나? (7.1)
- [ ] **결론 절의 제목과 범위 서술** — "남은 세 전략", "네 전략까지" 같은 진행
      상황이 제목에 박혀 있지 않나? (7.7)
- [ ] **폐기 기록** — 회수한 전제를 지우지 않고
      `docs/results/discarded-measurements.md`로 옮겼나?

**표를 채우는 일은 이슈에 있고 전제를 회수하는 일은 어느 이슈에도 없다.** 그래서
체크리스트로 둔다.

**«측정»이 아니어도 모양이 같으면 이 규칙이다.** #202는 측정이 아니라 **확인**이었다
— 크레딧을 받을 경로 셋이 전부 막혔다는 사실을 웹에서 확인한 문서 PR이다. 그
사실이 `infra-decision.md` 5절의 *"받은 크레딧 잔량을 확인한다"*를 무효화했는데
**같은 PR에서 그 줄을 안 고쳤고**, #203이 그것을 따로 잡아야 했다.

**1번(구현이 문서와 갈리면)으로는 안 걸린다.** 코드가 문서와 갈린 것이 아니라
**문서가 문서를 무효화했다.** 그래서 이 규칙의 범위를 «측정을 반영하는 PR»이 아니라
**«새 사실을 세우는 PR»**로 읽는다 — 위 체크리스트가 측정 어휘로 적혀 있을 뿐,
묻는 것은 *"이번에 확정한 것이 어딘가의 전제를 무너뜨렸나"* 하나다.

### 3. 시제가 든 문장에는 마일스톤 표식을 붙인다

"아직 구현되지 않았다"는 쓸 수 있다. 다만 **언제 기준인지 함께 적는다** —
"(M2 기준)". 그 마일스톤이 지나면 무조건 재확인 대상이 된다.

표식이 없어서, `load-test/README.md`의 "예약 API는 아직 구현되지 않았다"가
60회를 측정한 뒤에도 그대로 남아 있었다.

### 4. 절 제목에 진행 상황을 넣지 않는다

"네 전략까지", "남은 세 전략"은 본문에 쓸 말이지 제목에 쓸 말이 아니다. 제목에
박히면 본문만 갱신했을 때 둘이 어긋난다.

### 5. 파일을 추가·개명하면 그 디렉토리 README의 트리를 같은 PR에서 고친다

`load-test/README.md`의 구성 트리에서 파일 다섯 개가 빠져 있었다. 트리는 처음 쓸
때 한 번 만들고 그 뒤로 아무도 손대지 않았기 때문이다.

### 6. 미래형 조건 액션은 해소 조건과 함께 적고, 조건이 충족된 PR에서 회수한다

"부하 테스트에서 데드락이 계속 관측되면 개별 락으로 전환한다"처럼 **조건부로 적어
둔 대비책**은 조건이 판정된 순간 닫는다. 닫지 않으면 이미 결론이 난 문제가
미해결로 보인다.

### 7. 목록 안의 순번으로 참조하지 않는다. 절을 삽입할 때는 하위 절로 단다

**"7.4-5"처럼 목록 안의 순번을 가리키는 참조는 그 목록에 항목이 추가되는 순간
조용히 깨진다.** 링크가 아니라 숫자라서 아무도 알아채지 못하고, 다음 사람은 엉뚱한
단계를 읽는다. **절 제목이나 내용으로 참조한다** — "7.4의 재초기화 단계",
"프로토콜의 메트릭 캡처 단계".

**절 번호 자체(`7.4`, `4.5.1`)는 참조해도 된다.** 대신 **절을 삽입할 때 기존
번호를 밀지 않는다** — 새 절은 하위 절로 단다. `7.2.1`(데드락 회피 검증)과
`7.4.2`(세션 분할·대조군)가 그 형태다.

이 규칙은 두 번 겪고 세웠다.

| 언제 | 무슨 일 |
|---|---|
| `7.2.1` 삽입 | 같은 층위에 넣었으면 **상호 참조 30건이 밀렸을 것**이라 하위 절로 달았다 |
| `7.4.2` 삽입 | 프로토콜 목록에 단계가 하나 늘어 `load-test/README.md`의 **`7.4-5`가 깨졌다** |
| `rfp-scope.md` 5.2 삽입 | 하위 절로 달지 않고 같은 층위에 넣어 **`5.2`가 둘이 됐고**, 본문이 없는 절(`5.4`)을 가리켰다. `5.1.1`로 내려 고쳤다 — 번호를 밀지 않았으므로 다른 참조는 손대지 않았다 |

**두 번째는 하위 절 규칙만으로는 막지 못한다.** `7.4.2`는 규칙대로 하위 절로
달았는데도, 깨진 것은 절 번호가 아니라 **7.4 본문 목록의 순번**이었기 때문이다.
그래서 규칙이 둘이다 — 절은 하위로 달고, 목록 순번은 아예 참조하지 않는다.

### 8. PR을 쌓지 않는다. 새 작업은 언제나 main에서 브랜치를 판다

**이전 PR이 아직 머지되지 않았어도 base는 main이다.** 앞선 PR의 브랜치를 base로
삼으면 그 PR이 머지되는 순간 두 가지가 동시에 깨진다.

- **squash 머지가 해시를 바꾼다.** 같은 내용이 뒤 브랜치에는 원래 커밋으로,
  main에는 스쿼시 커밋으로 들어간다. 공통 조상은 그 이전이므로 **git은 양쪽이
  각각 고친 것으로 보고 충돌을 낸다.** 내용이 한 글자도 다르지 않아도 그렇다
- **base 브랜치가 삭제된다.** `--delete-branch`로 머지하면 뒤 PR은 base를 잃고,
  GitHub이 **재오픈도 base 변경도 거부한다**(`Cannot change the base branch of a
  closed pull request`). PR을 새로 여는 것 말고 방법이 없다 — 그 PR에 달린 리뷰
  대화는 따라오지 않는다

| 언제 | 무슨 일 |
|---|---|
| #98 → #99 → #100 | #98이 squash로 들어가며 #99가 충돌. 파일 두 개, 충돌 구간 9개가 **전부 같은 내용의 다른 커밋**이었다 |
| 같은 건 | #99의 base(`feat/demo-race-improvements`)가 지워져 되살릴 수 없었다. #111로 다시 열었다 |

**앞 PR의 결과물이 정말 필요하면** 그 PR을 먼저 머지하고 main을 당겨 받는다.
기다리는 시간이 아까워 쌓는 것인데, 위 표가 그 시간보다 비쌌다.

**이미 쌓아 버렸다면** 뒤 브랜치에 main을 병합해 푸는 것으로 충분하다. 다만
"어느 쪽을 취했는지"가 아니라 **"왜 그쪽이 양쪽을 다 담는지"**를 커밋 메시지에
남긴다 — 같은 내용의 다른 커밋이라 겉으로는 한쪽을 덮은 것과 구분되지 않는다.

### 9. 소유권을 옮길 때 `CODEOWNERS`와 `roles.md`를 함께 고친다

**한쪽만 고치면 둘이 다른 말을 하고, 사람은 대개 문서 쪽을 읽는다.**

`.github/CODEOWNERS`는 GitHub이 리뷰어를 붙이는 데 쓰는 **기계용 파일**이고
`docs/roles.md`는 **사람이 읽는 표**다. 같은 사실을 두 곳이 지키므로, 옮길 때
둘을 한 PR에서 고친다. 1번 규칙("구현이 문서와 갈리면 같은 PR에서 문서도
고친다")의 같은 형태이며, 여기서는 **구현이 아니라 설정이 정본**이다.

| 언제 | 무슨 일 |
|---|---|
| #77 — `notification/` 소유를 최건으로 이관 | **CODEOWNERS만 고쳤다.** `roles.md` 담당 표는 박태준으로 남았고, 그 아래 "CODEOWNERS가 이 표를 그대로 반영한다"가 그동안 거짓이었다 |
| 그 사이 | **계획서 발표 자료가 낡은 쪽(`roles.md`)을 인용해 박태준 항목으로 나갔다** (#130) |

**틀린 쪽을 고를 때는 설정이 이긴다.** CODEOWNERS는 PR마다 실제로 동작하므로
어긋나면 곧 드러나지만, 문서는 아무도 실행하지 않아 조용히 남는다.

**확인은 한 줄이면 된다.** `roles.md`의 담당 표와 CODEOWNERS의
`holdfast/` 경로를 맞춰 보는 것으로 충분하다 — 소유권을 옮기는 PR에서 그 대조를
한 번 돌린다.

## 하지 말 것

**`.gitignore`의 `*.tfstate`, `.terraform/`, `.env`를 지우지 않는다.** 빠지면 AWS 리소스 구성과 자격증명이 통째로 공개된다.

**AWS는 정적 액세스 키 대신 OIDC를 쓴다.** IAM에 GitHub OIDC Provider를 등록하고 Role ARN만 Environment secret으로 넣는다. secret scanning의 push protection이 켜져 있어 키가 커밋되려 하면 push가 막히지만, 애초에 만들지 않는 것이 낫다.

**`terraform apply`를 자동화하지 않는다.** `plan`까지만 CI에서 돌리고 `apply`는 수동으로 한다. 학생 계정에서 사고가 나면 요금이 붙는다.

**main에서 직접 작업하지 않는다.** 브랜치를 만든 뒤 프롬프트가 바뀐 것을 확인하고 시작한다. main에 커밋한 뒤 push하면 규칙 위반으로 거부되고, 커밋을 옮기는 작업이 추가로 필요해진다.

**PR을 쌓지 않는다.** 머지되지 않은 PR의 브랜치를 base로 새 브랜치를 파지 않는다. squash 머지로 해시가 달라져 충돌이 나고, base 브랜치가 삭제되면 뒤 PR은 되살릴 수 없다. 근거와 실제 사례는 위 8번에 있다.

**소유권을 한쪽에만 반영하지 않는다.** `CODEOWNERS`를 고치면 `roles.md`도 같은 PR에서 고친다. 근거와 실제 사례는 위 9번에 있다.

## 자주 쓰는 명령

```bash
# 내가 만든 브랜치 확인
git branch --show-current

# 열려 있는 내 이슈
gh issue list -R inhalab/holdfast --assignee @me

# PR 상태
gh pr status

# 특정 PR의 CI 로그 (실패 시)
gh run view --log-failed
```

## 사고 복구

**main에 실수로 커밋했을 때** — 커밋을 새 브랜치로 옮기고 main을 되돌린다.

```bash
git switch -c feat/작업이름          # 현재 커밋을 그대로 가진 브랜치 생성
git switch main
git reset --hard origin/main         # main만 원격 상태로 복구
git switch feat/작업이름
```

**커밋을 날렸을 때** — `git reflog`에서 해시를 찾아 복구한다.

```bash
git reflog                           # q로 나감
git reset --hard <해시>
```

## Git Bash 사용 시 주의

여러 줄을 한 번에 붙여넣으면 중간에 잘리거나 `[200~` 같은 문자가 섞인다. **한 줄씩 실행하고 프롬프트가 `$`로 돌아온 것을 확인**한 뒤 다음 줄로 넘어간다.

긴 파일을 만들 때는 heredoc(`cat > file <<EOF`) 대신 에디터를 쓴다. 마크다운 문서는 특히 VS Code로 직접 편집한다. 다른 에디터를 거치면 `\#`, `\*\*`처럼 이스케이프되어 렌더링이 깨질 수 있다.
