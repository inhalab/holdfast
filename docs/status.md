# holdfast 현황 — 이 문서 하나로 파악하기

**마지막 갱신: 2026-09-06 (M5 진행 중)**

이 문서는 요약이다. 모든 항목은 상세 문서로 링크되어 있고, **판단의 근거는 그쪽에
있다.** 여기서 결론이 궁금하면 그 링크를 따라가라.

## 1. 무엇을 하는 프로젝트인가

**국립중앙과학관 예약 시스템 RFP를 원본으로 삼아, 그중 동시성 제어 하나를 깊게 판
학부 2인 프로젝트다.**

| | |
|---|---|
| 요구사항 원본 | 국립중앙과학관 통합 예약 시스템 구축 RFP — 요구사항 **40개** |
| 실제로 판 영역 | 좌석 예약의 **동시성 제어**: 락 전략 5종 구현·측정 |
| 왜 그 영역인가 | RFP 평가 배점에 **"시스템 안정성 — 동시성 제어, 부하 분산, 예약 무결성"이 독립 항목 10점**이다. 여기에 "시스템 구현 방안" 15점을 더하면 90점 중 25점이 이 프로젝트가 판 자리다 |
| 발표 | **2026-12-07** |
| 인원 | 2명 (Asirante, F3ZLoV) |

**요구사항을 전부 이행하는 프로젝트가 아니다.** 40개 중 온전히 충족한 것은 4개다.
발표에서는 **"요구사항을 발췌해 그중 하나를 깊게 판 프로젝트"**로 말한다. 근거와
전체 목록은 [`rfp-scope.md`](rfp-scope.md).

### 기술 스택

Spring Boot 4.1.1 / Java 25 / Gradle 9.1 · PostgreSQL 18 · Redis 7 + Redisson 4.7
· Flyway · Thymeleaf + htmx · nginx(앱 2대 로드밸런싱) · k6 · Testcontainers 2.x

**Gradle 래퍼는 `api/`에 있다.** 모든 Gradle 명령은 `cd api`를 포함한다.

## 3. M3 결론 — 이 프로젝트의 본체

전체는 [`results/m3-conclusion.md`](results/m3-conclusion.md). 전략당 3회 × 3경합도
+ 세션마다 `none` 대조군, **총 60회.**

> 락이 없으면 경합이 있을 때 깨진다. 락을 거는 방식은 넷이 서로 다르지만 결과는
> 모두 초과 확정 0이다. **앱 락이 바꾼 것은 경합이 드러나는 방식이지 정합성이
> 아니며, 정합성의 최종 책임은 DB 제약과 조건부 UPDATE가 진다.** 성능은 전략을
> 구분하지 못했는데, 이 응용의 임계 구역이 서브밀리초이기 때문이다 — 그것은
> 결함이 아니라 홀드·확정을 분리한 설계의 결과다.

고경합(10석 / 500 VU), 3회 중앙값:

| 전략 | 초과 확정 | p95 | 같은 세션 `none` | 비율 |
|---|---|---|---|---|
| **none** | **5 · 4 · 3** ✗ | 40ms | — | — |
| pessimistic | 0 · 0 · 0 ✓ | 32ms | 41ms | 0.78 |
| optimistic | 0 · 0 · 0 ✓ | 41ms | 33ms | 1.25 |
| unique | 0 · 0 · 0 ✓ | 35ms | 20ms | 1.79 |
| redis | 0 · 0 · 0 ✓ | 18ms | 18ms | 1.01 |

60회 전부 5xx 0건 · 미분류 0건. 데드락도 다섯 전략 전부 0건.

### 이 결론에서 가장 자주 오해되는 두 가지

**"p95가 전략을 구분하지 못한다"는 곧 "빠르다"가 아니다.** 그 p95는 사실상
**409 거절의 p95**다 — 약 59,000건 중 락 경로를 실제로 지나는 것은 20건(0.034%)
뿐이다. 성공 요청만의 p95는 표본이 40~106건이라 **어떤 통계도 안정적이지 않아
병기하지 않기로 했다.** 근거는 m3-conclusion 2.5·3.5.

**비율 열을 전략 간 성능 비교로 읽으면 안 된다.** `none`을 여섯 번 재면 p95가
17.6~40.2ms(2.28배)로 흔들린다. **잡음 바닥이 판정 대상보다 크다.**

### 화면별 응답시간 — 검수 기준 PER-002 (#105)

전체는 [`results/per-002-page-timing.md`](results/per-002-page-timing.md).
**위 p95와 다른 값이다** — 저쪽은 홀드·확정 API이고 이쪽은 서버렌더 화면이다.

13개 화면 × 두 부하 조건(무부하 · 저경합 배경), 조건당 3회 중앙값.

| | p95 | 기준 대비 |
|---|---|---|
| 가장 느린 화면 — 관리자 예약 현황 | **45.9ms** | **1.5%** |
| 좌석맵 (1000석) | 22.9ms | 0.8% |
| 나머지 열한 개 | 1.4~16.4ms | 0.6% 이하 |

**26개 값 전부 3초 아래이고 가장 좁은 여백이 65배다.** 6회 전부 2xx 아닌 응답
0건 · 정적 자원 실패 0건.

**그래도 "PER-002 충족"이라고 쓰지 않는다.** 원문이 지정한 화면 중
**정산확인·검색결과 조회 둘이 없다.** 있는 화면이 기준을 지키는 것과 지정된
화면이 다 있는 것은 다른 문제다.

**두 조건의 차이는 해석하지 않는다.** 조건 간 차이가 회차 간 폭 안에 들어간다 —
말할 수 있는 것은 "이 부하에서 화면이 밀려 올라간 흔적이 없다"까지다.
**한 벌을 버렸다** — 조건을 몰아서 배치했더니 JIT 드리프트가 조건 효과로 읽혀
부하 중이 무부하보다 빨랐다(7.8.4와 같은 함정).

## 4. 구현 현황

### 되는 것 — 최소 완결선

**좌석 선택 → 선점 → 결제(Mock) → 확정 → QR 발급 → 검표**가 브라우저에서 끊김
없이 돈다. `MinimumScopeFlowTest` 8건이 이 흐름 전체를 지킨다.

**어느 사용자로 해도 돈다.** 이 문장은 #126 이전에는 **사용자 1에서만** 참이었다 —
결제 뒤 예약 확인으로 가는 이동이 `?userId=`를 잃어 사용자 2는 자기 티켓 앞에서
404를 만났다. 서버 리다이렉트가 아니라 브라우저의 `window.location.href`라
`MinimumScopeFlowTest` 8건이 통과하는 동안 그랬다(`design-spec.md` 5.4).

화면: 프로그램 목록 → 회차 목록 → 좌석맵 → 예약 확인 → 티켓 → 검표, 그리고
**예약 조회(비회원·마이페이지)**, 관리자(예약 현황·프로그램/회차 등록·좌석배치
등록), 동시 요청 데모.

**충족 4 · 부분 8 · 나머지는 미구현이거나 의도적 제외.** 항목별 표는
[`rfp-scope.md`](rfp-scope.md) 3장.

|---|---|
| 부분 | SFR-002~006 · **PER-002**(화면별로 다 쟀고 전부 통과 — 남은 것은 없는 화면 둘) · SIR-002 · TER(테스트 140건) |
| 미구현 | SFR-007(인증) |

### 의도적으로 제외한 것

**"못 해서 안 한 것"과 "안 하기로 판단한 것"을 구분한다.**

| | 예 | 왜 |
|---|---|---|
| **할 수 없다** | 실제 PG·SMS 연동, 개인정보 보호 체계, 기존 시스템 연계 | 계약·법령·조직에 의존 |
| **가치가 낮다** | **인증**, 파일 업로드, 대기열, 전자정부 표준프레임워크 | 인증은 **측정 하네스를 깬다** — k6가 `X-User-Id`로 사용자를 구분한다. 표준프레임워크는 옮기면 M3 측정을 전부 다시 해야 하고 얻는 것이 없다 |
| **열람할 수 없다** | 네트워크 구성도, 하드웨어·소프트웨어 현황, 업무구성도 | 「행정기관 및 공공기관 정보시스템 구축·운영 지침」 제17조 대상이고 학생 신분으로 열람 근거가 없다. **평가 배점의 "현행 시스템 분석"(사업 이해도 10점)을 충족할 수 없는 이유**이며, design-spec 1.3이 As-Is 없이 신규 구축을 전제한 근거다 |

## 5. 되돌리면 안 되는 판단

**여기 있는 것을 바꾸면 측정이 무효가 되거나 이미 해결한 문제가 되살아난다.**

### 설계

| 판단 | 왜 |
|---|---|
| **전략 밖 코드에 전략별 분기를 넣지 않는다** | `SeatHoldStrategy` 구현체 5개를 `@ConditionalOnProperty`로 하나만 띄운다. 분기가 새면 "무엇을 측정했는가"가 흐려진다 |
| **홀드와 확정을 분리한다** | 임계 구역이 서브밀리초인 이유이자 M3 결론의 근거다 |
| **좌석재고·할당량 행을 미리 만든다** | 이것이 없으면 행 단위 락과 유니크 제약을 둘 다 쓸 수 없다 |
| **CS-6: 사용자 할당량 행을 좌석보다 먼저 잠근다** | 같은 사용자의 동시 요청이 완전히 직렬화된다. 데모에서 요청마다 `X-User-Id`를 다르게 보내야 하는 이유 |
| **U-2는 `none`에서만 없앤다** | `none`은 "락 없이 돌리면 몇 건 깨지나"의 베이스라인이다. 제약을 걸면 실패 데이터를 못 얻는다. **U-2는 앱이 아니라 스키마에 있다** — `docker compose up`만으로는 안 지워지고 `seed.sh`가 지운다 |
| **read-then-act 대신 조건부 UPDATE + `rowsAffected`** | Outbox 클레임과 좌석 확정이 같은 관용구를 쓴다 |
| **결제가 확정과 같은 트랜잭션에 있다** | 실제 PG로는 성립하지 않는다는 것을 [`scope-m4.md`](scope-m4.md) 5절에 명시했다 |
| **결제에 환불 상태를 두지 않는다. 티켓에 `VOID`도 두지 않는다** | 둘 다 예약 상태의 순수 함수라 **새 사실을 담지 않고**, 취소 트랜잭션에 쓰기를 더하면 CS-4의 임계 구역이 길어진다. 없는 절차를 "환불 완료"라고 적으면 감추는 것보다 나쁘다 — 근거 넷은 [`erd.md`](erd.md) 4절, 판정은 #106 |

### 측정

| 판단 | 왜 |
|---|---|
| **7.3의 고정 변수를 시연 편의로 바꾸지 않는다** | nginx `worker_connections` 8192, Tomcat max-threads 200, Hikari 풀, 홀드 TTL 10초, 측정 대상 커밋 |
| **AWS 재측정 약속은 회수했다** | 로컬 동거(k6가 앱과 같은 머신)를 확정된 한계로 못박았다 |
| **`classify.js`의 버킷을 건드리지 않는다** | 정상 거절·오류·락 포기가 섞이면 모든 비교가 무너진다. favicon 404에 `ErrorCode`를 새로 만들지 않은 이유 |

### 운영·인프라

| 판단 | 왜 |
|---|---|
| **리다이렉트는 상대 경로** (`use-relative-redirects`) | 절대 URL은 프록시가 넘긴 `Host`에 의존한다. nginx는 그것을 다시 절대화하므로 `Host $http_host`도 함께 필요하다 — 실측 표는 [`design-spec.md`](design-spec.md) 5.4 |
| **플래시 메시지를 쓰지 않는다** | 앱이 2대라 세션이 로드밸런서를 못 넘는다. sticky session은 측정 고정 변수를 건드린다. 검증 실패는 그 자리에서 화면을 다시 그린다 — 5.5 |
| **id를 명시하는 시드는 IDENTITY 시퀀스를 맞춘다** | 안 맞추면 앱의 자동 생성 INSERT가 이미 있는 id를 받는다 — [`erd.md`](erd.md) 2.1 |
| **적용된 Flyway 마이그레이션은 주석도 안 고친다** | 체크섬이 바뀌어 기존 DB가 기동을 거부한다 |
| **PR을 쌓지 않는다** (R8) | squash로 해시가 달라져 같은 내용이 충돌하고, base 브랜치가 지워지면 되살릴 수 없다 — [`workflow.md`](workflow.md) |
| **`/demo/**`는 끌 수 있고 기본값은 켬이다** | `holdfast.demo.enabled=false`로 끈다. 되돌리기가 한 회차의 좌석·홀드·예약을 지우므로 **로컬 시연 밖에서 켜 두지 않는다**. 기본값이 켬인 것은 이 프로젝트의 실행 환경이 로컬 Docker Compose뿐이기 때문이다(`infra-decision.md` 2절) — [`scope-m4.md`](scope-m4.md) 7절 |
| **CI가 이미지 기동까지 본다** | `boot` 잡이 `./holdfast rebuild`로 스택을 띄우고 **다섯 컨테이너 전수 + 앱 두 대 응답 + 화면 렌더**를 확인한다. 테스트는 `properties=`로 값을 직접 주므로 `application.yml`의 자리표시자 경로를 건너뛴다 — 그래서 **테스트가 전부 통과해도 컨테이너가 못 뜬 적이 두 번 있다**(#143, #148) — #144 |
| **실행기는 전략 이름을 검증한다** | `holdfast`가 전략 하나만 받고 다섯 중 하나인지 본다. 안 하면 없는 이름이 그대로 `HOLDFAST_STRATEGY`로 나가고 **조건에 맞는 빈이 0개가 되어 앱이 기동하지 못한다**. 실제로 `extreme`(경합도 시나리오)이 들어가 main이 안 떴다 — #143 |
| **`/admin/**`은 아무나 연다. 배포하면 끈다** | 인증이 없다. 로컬은 노출이 없어 그대로 두고, #42(AWS)로 뜨면 `holdfast.admin.enabled=false`로 **경로 자체를 없앤다** — 잠그는 것이 아니다. 네 수단을 따져 그것을 고른 근거는 [`infra-decision.md`](infra-decision.md) 3.1. **구현됐다(#124)** — `false`면 컨트롤러 셋의 빈이 만들어지지 않아 경로가 404이고, 바닥 내비의 링크도 같은 값으로 사라진다 |

## 6. 버린 것과 회수한 것

**"틀린 값"과 "틀린 결론"을 구분해 따로 기록한다.** 전체는
[`results/discarded-measurements.md`](results/discarded-measurements.md).

### 폐기한 측정 4건 — 값이 오염됐다

| # | 무엇을 재고 있었나 | 조치 |
|---|---|---|
| 1 | 락 전략이 아니라 **nginx 커넥션 상한**(기본 512 고갈) | 8192로 고정 |
| 2 | 경합이 아니라 **매진 상태의 거절 처리량** (재초기화 TRUNCATE 데드락) | 행 단위 DML + 재시도 |
| 3 | 전략의 정합성이 아니라 **측정 장치가 만든 고아 상태** | 재초기화가 좌석 행을 먼저 `FOR UPDATE` |
| 4 | 임계 구역이 아니라 **죽은 로드밸런서에 대한 연결 실패** (nginx가 1시간 45분 전에 종료돼 있었다) | `run.sh`에 사전 점검 |

**3번의 수정은 재측정으로 검증됐다** — `none`의 저경합 초과 확정은 일부가 아니라
**전부가 아티팩트**였다.

### 회수한 판정 2건 — 값은 맞고 문장이 틀렸다

| | 무엇 | 왜 |
|---|---|---|
| **C** | 7.8.2 "임계 구역이 길어지면 성능 결론이 갈린다" | **대조군 하나로 판정한 표본 부족.** `none`을 여섯 번 재니 p95가 2.28배로 흔들려 **잡음 바닥이 판정 대상(27%)보다 컸다.** 숫자는 지금도 유효하다 |
| **A** | 경합도 교차점 기대 (낙관/비관이 어디선가 뒤집힌다) | **교차점이 없었다.** 사전 가설이 빗나갔고, 그 사실 자체를 결과로 남겼다 |

*(B — AWS 재측정 약속 — 은 판정이 아니라 회수한 약속이라 5절에 있다.)*

## 8. 실행 방법

**모든 진입점은 저장소 루트의 `./holdfast` 하나다.** 각 스크립트를 직접 부를 수도
있고, 이 파일은 "무엇을 언제 쓰는가"를 모아 둔 것이다.

```bash
./holdfast              # 서브커맨드 목록
./holdfast up           # 앱 2대 + DB + Redis + nginx 기동 (nginx 설정 reload 포함)
./holdfast demo none    # 시연 준비 — 기동 + 시드 + 화면 주소 안내
./holdfast strategy redis   # 전략을 바꿔 앱만 다시 띄운다 (약 13초, 시드도 함께)
./holdfast down
```

측정과 검증:

```bash
./holdfast measure                       # 대화형
./holdfast measure --preset m3-all       # 5전략 × 3시나리오 (45회)
./holdfast verify                        # DB 검증 쿼리 V-1~V-5
./holdfast summary                       # 결과 요약 (기본: 최신 세션)
cd api && ./gradlew test                 # 140건
```

### 화면 주소 (`./holdfast demo` 뒤)

| 화면 | 주소 |
|---|---|
| 프로그램 목록 (진입점) | `http://localhost:8080/` — `/programs`도 같은 화면이다 |
| 회차 목록 | `/programs/{프로그램}` |
| 좌석맵 | `/sessions/1?userId=1` — 창을 둘 띄워 사용자를 바꾼다 |
| **예약 확인 · 티켓(QR)** | `/reservations/{예약}?userId={소유자}` — 예약 뒤에 여기로 온다. 소유자가 아니면 404다 |
| 예약 조회 (비회원) | `/reservations/lookup` — 예약번호 + 예약자 번호 |
| 마이페이지 | `/my/reservations?userId=` — 그 사용자의 예약 목록 |
| 동시 요청 데모 | `/demo/race` |
| 검표 | `/scan` |
| 관리자 — 예약 현황 | `/admin/reservations` |
| 관리자 — 프로그램·회차 | `/admin/programs` |
| 관리자 — 좌석배치 | `/admin/layouts` |

**주소를 외울 필요는 없다.** 모든 서버렌더 화면 바닥에 내비가 있고(#121), 관리자
예약 현황의 예약번호·회차 열이 각각 예약 확인과 좌석맵으로 이어진다. 어디서
어디로 갈 수 있는지는 [`scope-m4.md`](scope-m4.md) 8절의 표에 있다.

**시연에서 주의할 것 셋.**

1. **첫 실행은 한 번 눌러 버리고 시작한다.** JVM이 데워지기 전 첫 묶음은 일부
   요청이 연결 단계에서 실패한다
2. **동시 요청 데모의 좌석은 1개가 가장 선명하다.** 브라우저는 호스트당 커넥션이
   6개라, "흩뿌리기" 방식에서 좌석이 6개 이상이면 동시 요청이 서로 다른 좌석으로
   갈라져 **`none`도 초과 홀드를 내지 않는다.** 기본값인 "좌석마다 차례로"는 이
   제약을 우회한다 — [`scope-m4.md`](scope-m4.md) 7절에 실측 표가 있다
3. **`none`인데 U-2가 남아 있으면 `none`이 아니다.** 화면이 경고를 띄운다
