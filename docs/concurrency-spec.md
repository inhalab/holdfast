# 동시성 설계서

**holdfast** — 좌석 단위 점유 제어 · 락 전략 비교

`docs/design-spec.md` 3.4절이 지정한 별도 문서다. 임계 구역이 어디인지, 각 전략을 어떻게 구현하는지, 무엇을 어떤 조건에서 측정하는지를 착수 전에 고정한다.

### 0.1 버전 근거

Spring Boot 4.0은 2025-11-20, 4.1은 2026-06-10에 공개됐다. 3.x는 3.5.16(2026-06-25)을 끝으로 오픈소스 지원이 종료됐고 현재 지원 대상은 4.0·4.1뿐이다. 4개월 프로젝트를 지원 종료된 라인에서 시작할 이유가 없다.

Redisson 4.7.0은 Spring Boot 1.3.x–4.1.x를 지원하므로 호환성 문제는 없다. Valkey도 같은 클라이언트로 붙는다.

**Spring Boot 4 전환 비용은 인지하고 들어간다.** Jakarta EE 11 기반, Spring Framework 7 필수, Gradle 9 이상, Jackson 3 기본, JSpecify 기반 null 애노테이션. 3.x에서 deprecated였던 API는 제거됐다. 인터넷 예제 대부분이 3.x 기준이라 설정·의존성 쪽에서 그대로 붙지 않는 경우가 생긴다. 다만 이 문서가 다루는 `@Lock`, `@Transactional`, `TransactionSynchronizationManager`, Redisson `RLock`은 4.x에서 변경이 없다.

### 0.2 DB 선택 근거

MySQL 8.0도 `FOR UPDATE SKIP LOCKED`와 `NOWAIT`을 지원하므로 Outbox 처리에서는 차이가 없다. 갈리는 지점은 하나다.

**InnoDB는 동일 유니크 키에 INSERT가 몰릴 때 갭 락과 insert-intention 락이 얽혀 데드락이 발생할 수 있다.** READ COMMITTED로 낮춰도 유니크 키 검사 경로에서는 남는다. Postgres는 speculative insertion으로 처리해 유니크 위반 오류만 반환한다.

따라서 MySQL에서 측정하면 `unique` 전략 행의 숫자가 제약 방식의 특성인지 InnoDB 구현 아티팩트인지 구분되지 않는다. 5개 행 중 하나가 DB 구현에 오염되는 것을 피하기 위해 Postgres를 택한다.

**대신 `deadlock_timeout`을 낮춘다.** Postgres는 기본 1초를 대기한 뒤에야 데드락을 검사하므로, p95 3초가 검수 기준인 상황에서 데드락 한 건이 1초를 잡아먹는다. 측정 환경에서 200ms로 설정하고 그 값을 보고서에 명시한다. InnoDB는 대기 그래프로 즉시 탐지하므로 이 항목은 MySQL이 유리하다.

### 0.4 프론트엔드

Thymeleaf + htmx로 확정했다. `design-spec` 5.3이 좌석맵 최소 구현을 지시하고 있어 SPA의 이점이 크지 않고, 서버 렌더링으로 가면 담당자가 Java 하나만 쓰며 빌드 파이프라인·npm 의존성·CORS·별도 배포 대상이 모두 사라진다. 템플릿은 `api/src/main/resources/templates/`에 두므로 별도 `web/` 디렉토리는 만들지 않는다.

부하 테스트는 k6가 HTTP를 직접 호출하므로 프론트엔드 선택은 측정값에 영향을 주지 않는다.

| 항목 | 결정 |
|---|---|
| 좌석 상태 갱신 | 좌석맵 fragment만 3초 폴링 (`hx-get` + `hx-trigger`) |
| 좌석 선택 상태 | **클라이언트 보관** (hidden input 또는 JS 배열) |
| 전체 페이지 새로고침 | 사용하지 않음 |

**좌석 선택 상태를 서버 세션에 두지 않는다.** 앱 2대 구성에서 세션 공유 문제가 생기고, 이는 측정 대상인 동시성과 무관한 변수를 하나 더 만든다. 스티키 세션으로 우회하면 부하 분산이 왜곡되어 측정 자체가 오염된다.

좌석재고는 `(회차ID, 좌석ID)` 행으로 **사전 생성**한다. 예약 시점 생성이 아니다. 이 결정이 없으면 행 단위 락과 유니크 제약을 둘 다 쓸 수 없다.

## 1. 임계 구역

| # | 구역 | 경합 대상 | 위험 |
|---|---|---|---|
| CS-1 | 좌석 홀드 획득 | `seat_inventory` 행 | 초과 점유 |
| CS-2 | 예약 확정 | 홀드된 행 | 만료된 홀드의 확정 |
| CS-3 | 홀드 TTL 만료 | 홀드된 행 | 확정과 동시 발생 |
| CS-4 | 취소 시 좌석 반환 | 판매된 행 | 이중 반환 |
| CS-5 | 회차 잔여 수량 | `event_session.remaining` | 카운터 경합 |
| CS-6 | 1인 최대 매수 검사 | `(회차ID, 사용자ID)` 집계 | 상한 초과 |

**CS-2와 CS-3의 경합이 이 프로젝트에서 가장 자주 터진다.** 홀드가 만료되는 순간과 결제 완료 콜백이 도착하는 순간이 겹치면, 만료된 좌석이 확정되거나 결제는 됐는데 좌석이 없는 상태가 된다.

CS-5는 가급적 만들지 않는다. 잔여 수량을 별도 카운터 컬럼으로 두면 회차 단위 핫 로우가 생겨 좌석 단위 락의 의미가 사라진다. 잔여 수량은 `COUNT(*) WHERE status='AVAILABLE'`로 유도하고, 조회 성능이 문제되면 그때 캐시를 얹는다.

### 1.1 CS-6 — 좌석 락으로 막히지 않는 구역

REQ-03의 1인 최대 매수 제한은 좌석 경합과 **다른 축**이다. 같은 사용자의 요청 두 개가 서로 다른 좌석을 대상으로 동시에 들어오면, 각각 카운트 검사를 통과해 상한을 넘긴다. 좌석 단위 락은 이 경로를 전혀 막지 못한다.

집계 기준이 `(회차ID, 사용자ID)`이므로 잠글 대상도 그 단위여야 한다.

| 방법 | 내용 |
|---|---|
| **채택** | `user_session_quota (session_id, user_id, held_count)` 행을 사전 생성하고 좌석 락 **이전에** 이 행을 먼저 잠근다 |
| 대안 | Postgres advisory lock `pg_advisory_xact_lock(hash(session_id, user_id))` |

**락 획득 순서를 사용자 행 → 좌석 행으로 고정한다.** 역순이 섞이면 데드락이 난다. 5.1의 좌석 ID 정렬 규칙과 함께 전역 순서를 이룬다.

이 구역은 락 전략 비교 대상이 **아니다.** 5개 전략 전부에서 동일한 방식으로 처리해 변수를 늘리지 않는다.

## 2. 좌석재고 상태 전이

```
AVAILABLE ──hold──> HELD ──confirm──> SOLD
    ^                 │                 │
    └────expire───────┘                 │
    └────────────cancel─────────────────┘
```

`seat_inventory` 컬럼:

| 컬럼 | 용도 |
|---|---|
| `session_id`, `seat_id` | 복합 유니크 |
| `status` | AVAILABLE / HELD / SOLD |
| `hold_id` | 현재 홀드 식별자 (nullable) |
| `held_until` | 홀드 만료 시각 (nullable) |
| `version` | 낙관적 락용 |

### 2.1 두 개의 유니크 제약을 구분한다

이 문서에서 "유니크 제약"이라는 말이 두 곳에 쓰이는데 역할이 전혀 다르다. 섞으면 베이스라인이 성립하지 않으므로 여기서 고정한다.

| 제약 | 대상 | 역할 | 적용 |
|---|---|---|---|
| `seat_inventory (session_id, seat_id)` | 사전 생성된 재고 행 | 재고 행 중복 생성 방지 | **5개 전략 전부** |
| `seat_hold (session_id, seat_id)` | 홀드 레코드 | 초과 홀드 차단 — 최후 방어선 | **`none` 제외 4개** |

**앞의 것은 초과 예약을 막지 못한다.** 재고 행은 어차피 하나뿐이고, 초과 예약은 그 하나의 행을 두 요청이 각각 UPDATE하면서 발생한다. 행의 유일성과 점유의 유일성은 다른 문제다.

**초과 예약을 실제로 막는 것은 뒤의 것이다.** 따라서 `none` 베이스라인에서는 `seat_hold`의 유니크 제약을 **걸지 않는다.** 걸어두면 초과 예약이 0건으로 나와 2개월차 산출물인 실패 데이터를 얻을 수 없고, 나머지 4개 전략이 무엇을 고쳤는지 말할 근거가 사라진다.

제약을 끄는 방식은 마이그레이션 분기가 아니라 **인덱스 생성/삭제를 시드 스크립트에서 처리**한다. `holdfast.strategy=none`이면 측정 시작 전에 `DROP INDEX`, 그 외에는 `CREATE UNIQUE INDEX`. 스키마 파일은 하나로 유지된다.

### 2.2 seat_hold 테이블 — 5개 전략 공통

`unique` 전략만 별도 테이블을 쓰면 그 행의 숫자가 다른 전략과 비교 불가능해진다. **같은 자료구조 위에서 락 방식만 바꾸는 것이 비교의 전제다.** 따라서 `seat_hold`는 전략과 무관하게 항상 존재한다.

| 컬럼 | 용도 |
|---|---|
| `id` | PK |
| `session_id`, `seat_id` | 복합 유니크 (`none` 제외) |
| `hold_id` | 홀드 그룹 식별자 (여러 좌석 한 번에) |
| `user_id` | CS-6 집계용 |
| `held_until` | 만료 시각 |
| `status` | HELD / CONFIRMED / RELEASED |

`seat_inventory.status`와 `seat_hold`는 중복이 아니라 역할이 다르다. 전자는 좌석의 현재 상태를 읽기 위한 것이고, 후자는 홀드의 이력과 유일성을 보장하기 위한 것이다. 확정·만료 시 두 테이블을 같은 트랜잭션에서 갱신한다.

## 3. 홀드 정책

**TTL 5분.** 결제 화면 체류 시간을 고려한 값이며, 부하 테스트에서는 경합을 빨리 관찰하기 위해 10초로 낮춰 쓴다. 프로퍼티로 뺀다.

만료 처리 방식은 세 가지가 있다.

| 방식 | 내용 | 채택 |
|---|---|---|
| 스케줄러 배치 | 주기적으로 만료 행을 AVAILABLE로 | 보조 |
| 지연 큐 | Redis TTL + keyspace notification | 미채택 |
| **lazy 검증** | 조회·확정 시점에 `held_until` 비교 | **주** |

**lazy 검증을 주로 삼는다.** 확정 쿼리 자체에 만료 조건을 넣으면 CS-2와 CS-3의 경합이 단일 SQL 문 안에서 원자적으로 해소된다.

```sql
UPDATE seat_inventory
   SET status = 'SOLD', hold_id = NULL, held_until = NULL, version = version + 1
 WHERE session_id = ? AND seat_id = ?
   AND status = 'HELD'
   AND hold_id = ?
   AND held_until > now();
```

`rowsAffected = 0`이면 홀드가 만료됐거나 남의 홀드다. 별도의 사전 조회가 없으므로 "조회 후 확정" 사이의 틈이 존재하지 않는다. 스케줄러는 만료 행을 실제로 AVAILABLE로 되돌려 조회 성능을 유지하는 청소 용도로만 둔다. 스케줄러가 죽어도 정합성은 깨지지 않는다.

**시각 기준은 DB의 `now()`로 통일한다.** 앱 서버 2대의 시계가 어긋나면 만료 판정이 인스턴스마다 달라진다.

**이 확정 쿼리는 `none`을 제외한 4개 전략이 쓴다.** 조건부 UPDATE는 락이 아니라 올바르게 쓴 쿼리이고, 베이스라인은 아무 동시성 제어도 없는 순진한 구현이어야 하므로 확정도 SELECT 후 UPDATE로 한다. 근거와 그 결과는 `state-transitions.md` 2.1절에 있다 — 이 예외가 없으면 베이스라인이 검수 기준(초과 승인 0건)을 구조적으로 위반할 수 없어, 재현한 결점과 측정 기준이 어긋난다.

## 4. 락 전략

전략은 `SeatHoldStrategy` 인터페이스의 구현체 5개로 두고, `@ConditionalOnProperty(name="holdfast.strategy")`로 스위칭한다. k6 시나리오는 고정하고 프로퍼티만 바꿔 측정한다.

```java
public interface SeatHoldStrategy {
    HoldResult hold(HoldCommand command);
}

public record HoldCommand(long sessionId, long userId, List<Long> seatIds, String holdId) {}
```

**파라미터 나열 대신 커맨드 객체로 받는다.** 위 시그니처가 정하는 것은 "전략이 무엇을 받는가"이지 파라미터 나열 방식이 아니므로, 같은 정보가 담기면 이 절은 지켜진다. `sessionId`와 `userId`가 둘 다 `long`이라 나열 방식에서는 순서를 바꿔 넘겨도 컴파일이 통과하는데, 그 버그는 초과 예약을 만들면서 "락 전략이 샌 것"과 구분되지 않아 측정 결과 전체를 의심하게 만든다. 7.1이 지표별 출처를 못박은 것과 같은 이유로 원인이 뒤섞이는 경로를 사전에 차단한다. `userId`가 필요한 것은 전략이 `seat_hold`를 INSERT하기 때문이다(`user_id`는 CS-6 집계용이며 NOT NULL).

**홀드 TTL은 커맨드에 넣지 않는다.** 각 전략이 `holdfast.hold-ttl-seconds`로 직접 주입받는다. 호출 측이 TTL을 정하면 전략마다 다른 값이 들어갈 여지가 생겨 7.3의 고정 변수 통제가 깨진다.

| 프로퍼티 값 | 전략 |
|---|---|
| `none` | 베이스라인 (락 없음) |
| `pessimistic` | 비관적 락 |
| `optimistic` | 낙관적 락 |
| `unique` | DB 유니크 제약 |
| `redis` | Redis 분산락 |

### 4.1 베이스라인 (`none`)

조회 후 UPDATE. 락 없음. **전략이 아니라 실패 증거다.** 2개월차 산출물이며, 여기서 초과 예약 M건이 나와야 나머지 4개가 무엇을 고쳤는지 말할 수 있다.

**홀드뿐 아니라 확정도 순진하게 한다.** 홀드에서 초과 홀드(V-2)가, 확정에서 초과 확정(V-1)이 나온다. 확정까지 순진해야 하는 이유는 `state-transitions.md` 2.1절에 있다. `none`은 성능 비교 대상이 아니라 실패 증거이므로, 확정 경로가 나머지 4개와 다른 것이 비교를 오염시키지 않는다.

### 4.2 비관적 락 (`pessimistic`)

`@Lock(LockModeType.PESSIMISTIC_WRITE)` 또는 native `SELECT ... FOR UPDATE`. 트랜잭션 종료까지 행을 점유한다. 대기 중 DB 커넥션을 계속 쥐고 있다는 점이 성능 특성을 지배한다.

`FOR UPDATE NOWAIT` / `SKIP LOCKED` 변형은 측정하지 않는다. 범위가 늘어난다.

### 4.3 낙관적 락 (`optimistic`)

JPA `@Version`은 쓰지 않는다. 버전 증가가 flush 시점에 묶이고 `OptimisticLockException`이 트랜잭션 커밋 시점, 즉 `@Transactional` 메서드 바깥에서 터져 같은 트랜잭션 안에서 재시도할 수 없다.

명시적 조건부 UPDATE로 한다.

```sql
UPDATE seat_inventory
   SET status = 'HELD', hold_id = ?, held_until = now() + interval '5 minutes',
       version = version + 1
 WHERE id = ? AND version = ? AND status = 'AVAILABLE';
```

`rowsAffected = 0`이면 충돌.

**재시도 상한 3회, 지수 백오프 + 지터로 시작한다. 이 숫자는 설계값이 아니라 시작값이다.** 고경합 시나리오에서 재시도 분포를 관측한 뒤 조정하고, 조정 전후 값을 함께 기록한다. 재시도 횟수를 메트릭으로 노출한다 — 고경합에서 이 값이 폭발하는 것이 이 전략의 특성이다.

### 4.4 DB 유니크 제약 (`unique`)

앱 레벨 락을 **전혀 쓰지 않고** `seat_hold`에 INSERT한 뒤 `(session_id, seat_id)` 유니크 제약 위반을 잡는다. `DataIntegrityViolationException` → 409.

다른 전략과의 차이는 테이블이 아니라 **앱 레벨에서 무엇을 하느냐**다(2.2 참조). `pessimistic`·`optimistic`·`redis`도 같은 `seat_hold`에 INSERT하며, 그 전에 각자의 락을 잡을 뿐이다. 이 전략만 그 단계가 비어 있다.

따라서 이 전략에서 제약 위반은 **정상 동작**이고, 다른 전략에서 제약 위반은 **앱 락이 샜다는 신호**다. 같은 카운터가 전략에 따라 다른 의미를 갖는다는 점을 보고서에 명시한다.

### 4.5 Redis 분산락 (`redis`)

Redisson `RLock`. 키는 `lock:seat:{sessionId}:{seatId}`.

```
waitTime  = 1초
leaseTime = 10초 (명시 — 워치독 비활성화)
```

**`leaseTime`을 반드시 명시한다.** 생략하면 워치독이 30초 리스를 10초마다 자동 연장하는데, 락을 오래 쥐는 버그가 측정에서 가려지고 실행마다 결과가 달라진다.

**`waitTime`은 1초다.** 검수 기준 p95 3초 안에는 락 대기만이 아니라 DB 처리·앱 처리·네트워크가 모두 들어가야 한다(7.3의 시간 예산). 락 대기에만 3초를 주면 나머지에 쓸 예산이 남지 않아, 고경합 시나리오에서 REQ-10을 구조적으로 달성할 수 없게 된다. 1초 안에 락을 얻지 못한 요청은 포기하고 409 `LOCK_TIMEOUT`으로 거절하며, 그 비율은 7.6의 **락 포기율** 열로 따로 집계한다.

#### 4.5.1 이 락은 정합성을 보장하지 않는다

단일 Redis 노드 기반 락은 형식적 의미의 안전한 분산락이 아니다. GC 정지나 네트워크 지연으로 리스가 만료된 뒤에도 클라이언트가 락을 보유했다고 믿을 수 있고, Redlock 역시 이 비판을 벗어나지 못한다.

이 프로젝트에서 그럼에도 사용 가능한 이유는 **DB 유니크 제약이 최후 방어선으로 깔려 있기 때문이다.** 분산락은 DB 경합을 줄이는 성능 장치이고, 정합성의 최종 책임은 제약이 진다.

이 구조는 감춰야 할 약점이 아니라 측정으로 증명할 명제다. `redis` 행의 제약 위반 횟수가 0이 아니면 락이 샌 것이고, 그럼에도 초과 예약이 0건이면 계층 방어가 작동한 것이다. **"분산락은 성능 최적화이지 정합성 보장이 아니다"** — 이 결론을 숫자로 뒷받침한다.

## 5. 두 가지 규칙

### 5.1 데드락 회피 — 좌석 ID 정렬

여러 좌석을 한 번에 예약할 때 두 요청이 반대 순서로 락을 잡으면 데드락이 난다. **모든 전략에서 좌석 ID를 오름차순 정렬한 뒤 획득한다.** 애플리케이션 레벨에서 정렬하고, 쿼리에도 `ORDER BY id`를 넣는다.

```java
List<Long> ordered = seatIds.stream().sorted().toList();
```

Postgres는 `FOR UPDATE`에서 정렬 전 스캔 순서로 락을 잡을 수 있어 `ORDER BY`만으로 완전히 안전하지는 않다. 부하 테스트에서 데드락이 계속 관측되면 정렬된 ID를 한 건씩 개별 락으로 전환한다.

전역 락 순서는 **사용자 할당량 행(CS-6) → 좌석 행(오름차순)** 이다.

### 5.2 분산락 해제는 커밋 이후

커밋 전에 풀면 락을 걸지 않은 것과 같다. 다른 요청이 커밋되지 않은 상태를 읽는다. **흔한 실수이며 단위 테스트로는 잡히지 않고 부하 테스트에서만 드러난다.**

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override public void afterCompletion(int status) {
            if (lock.isHeldByCurrentThread()) lock.unlock();
        }
    });
```

`afterCommit`이 아니라 `afterCompletion`을 쓴다. 롤백 시에도 해제되어야 한다.

## 6. 멱등성

| 대상 | 키 | 저장 |
|---|---|---|
| 예약 요청 | `Idempotency-Key` 헤더 (클라이언트 UUID) | `idempotency_record` 유니크 |
| 결제 콜백 | PG 거래 ID | `payment.pg_tx_id` 유니크 |
| 알림 발송 | `(예약ID, 알림종류)` | `outbox` 유니크 |

`idempotency_record`에 요청 해시와 응답 본문을 함께 저장한다. 같은 키로 다른 본문이 오면 409를 반환한다 — 키 재사용 버그를 조용히 통과시키지 않는다.

Outbox 워커는 `SELECT ... FOR UPDATE SKIP LOCKED`로 집는다. 2대가 같은 행을 잡지 않으면서 한쪽이 죽어도 다른 쪽이 이어받는다. MySQL 8.0에도 있는 기능이므로 DB 선택 근거는 아니다.

## 7. 측정 설계

### 7.1 지표

| 지표 | 출처 | 목표 |
|---|---|---|
| 초과 확정 건수 (V-1) | DB 검증 쿼리 | **0 — 검수 기준**(REQ-01) |
| 초과 홀드 건수 (V-2) | DB 검증 쿼리 | 0 (`none`은 실패 증거라 예외) |
| 팬텀 홀드율 | k6 태그 (홀드 201 → 확정 실패) | 0에 수렴. 0이 아니면 계층 방어이거나 만료다 — 7.6.3 |
| p95 응답시간 | **k6 (정본)** | 3초 이내 |
| p99 응답시간 | k6 | 참고 |
| 처리량 (TPS) | k6 | 비교값 |
| 정상 거절률 (409) | k6 태그 | **실패 아님** |
| 락 포기율 | k6 태그 (`LOCK_TIMEOUT`·`RETRY_EXHAUSTED`) | **409율·오류율과 별도** — 7.6.1 |
| 오류율 (5xx·타임아웃) | k6 태그 | 0에 가깝게 |
| 낙관적 재시도 횟수 | 앱 커스텀 메트릭 | 참고 |
| 제약 위반 발생 횟수 | 앱 커스텀 메트릭 | 0 기대 |
| 커넥션 풀 대기 | `hikaricp.connections.pending` `.acquire` | **해석의 핵심** |

**응답시간의 정본은 k6다.** 검수 기준의 p95는 사용자 관점 수치이므로 클라이언트 측 측정을 채택한다. Actuator는 응답시간 대체재가 아니라 **커넥션 풀 관측 수단**으로 쓴다. Micrometer HTTP 타이머는 기본적으로 카운트·합계만 내보내며 백분위를 얻으려면 히스토그램 설정을 따로 켜야 하는데, 정본이 k6인 이상 켤 필요가 없다.

**정상 거절과 오류를 반드시 분리한다.** 좌석이 이미 팔려 409를 반환한 것은 시스템이 제대로 동작한 것이다. 뭉뚱그리면 "실패율 40%" 같은 무의미한 숫자가 나온다.

**`seat_hold`의 유니크 제약은 `none`을 제외한 4개 전략에 걸어둔다.** `unique`는 앱 락 없이 제약만으로 막는 경우이고, 나머지 셋은 앱 락이 있고 제약이 최후 방어선이다. `none`에서만 제약을 제거하는 이유는 2.1에 있다 — 걸어두면 베이스라인의 초과 예약이 0건이 되어 실패 증거를 얻을 수 없다.

`seat_inventory`의 유니크 제약은 5개 전부에 항상 걸어둔다. 이쪽은 재고 행의 유일성이지 점유의 유일성이 아니므로 측정에 영향을 주지 않는다.

### 7.2 경합도 3단계

| 시나리오 | 좌석 수 | VU | 관찰 목적 |
|---|---|---|---|
| 저경합 | 1000석 | 100 | 오버헤드 비교 |
| 고경합 | 10석 | 500 | 전략 차이 |
| 극단 | 1석 | 200 | 정합성 한계 |

한 조건으로만 재면 순위가 고정되어 비교가 심심해진다. 낙관적 락은 저경합에서 가장 빠르고 고경합에서 재시도가 폭발하며, 비관적 락은 반대다. **이 교차점을 숫자로 잡으면 "상황에 따라 다르다"가 아니라 "경합도 N 이상에서 뒤집힌다"고 말할 수 있다.**

#### 7.2.1 데드락 회피 검증 시나리오 (좌석 3석 동시 홀드)

**경합도 3단계는 요청당 1석을 유지한다.** 여러 좌석을 한 번에 잡으면 거절 사유가
좌석별로 섞여(`api-spec.md` 4.2의 `conflicts`) 경합도별 숫자 해석이 흐려진다.

그런데 그러면 **5.1의 좌석 ID 오름차순 획득과 전역 락 순서가 부하 테스트에서 한
번도 실행되지 않는다.** 1석만 잡으면 정렬할 것이 없고, 여러 좌석을 잡는 코드
경로가 통째로 미검증으로 남는다. 데드락은 바로 그 경로에서만 난다.

그래서 **성능 비교가 아니라 데드락 검증만을 목적으로** 별도 시나리오를 둔다.

| 항목 | 값 |
|---|---|
| 요청당 좌석 수 | **3석** |
| 좌석 ID 전송 순서 | **무작위(뒤섞어 보낸다)** |
| 판정 기준 | **데드락 발생 0건** — 처리량·p95가 아니다 |
| 결과 기록 | 7.6 기록 양식에 넣지 않는다 |

**좌석 ID를 정렬하지 않고 보내는 것이 이 시나리오의 핵심이다.** 5.1이 정렬을
요구하는 주체는 애플리케이션이다. 클라이언트가 이미 정렬해 보내면 서버가 정렬을
빠뜨려도 데드락이 나지 않아, 서버의 정렬 로직이 실제로 도는지 확인할 수 없다.
두 요청이 반대 순서로 좌석을 요청해야 그 규칙이 시험된다.

**데드락 판정은 응답이 아니라 DB에서 읽는다.** 앱은 데드락을 잡아 409
`LOCK_TIMEOUT`으로 변환하므로(`api-spec.md` 3.3) k6가 받는 응답만으로는 그것이
데드락이었는지 단순 락 대기였는지 구분할 수 없다. 초과 예약과 같은 이유로
(7.1) 출처를 DB에 둔다.

```sql
-- 시나리오 실행 전후로 찍어 차이를 본다. 0이어야 한다.
SELECT deadlocks FROM pg_stat_database WHERE datname = current_database();
```

Postgres 로그의 `deadlock detected` 항목으로도 교차 확인한다. `deadlock_timeout`이
200ms로 낮춰져 있으므로(7.3) 데드락이 났다면 빠르게 검출된다.

**이 값이 0이 아니면 5.1의 규칙이 지켜지지 않은 것이다.** 그때는 정렬 누락을
찾거나, 5.1이 예고한 대로 정렬된 ID를 한 건씩 개별 락으로 전환하는 것을
검토한다 — Postgres는 `FOR UPDATE`에서 정렬 전 스캔 순서로 락을 잡을 수 있어
`ORDER BY`만으로 완전히 안전하지는 않기 때문이다.

#### 7.2.2 지속 경합 시나리오

**경합도 3단계는 락 대기를 재지 못한다.** `pessimistic` 실측에서 락 포기가
저경합 2건·고경합 1건·극단 4건으로 경합도와 무관하게 0에 수렴했다(7.6.1).
`lock_timeout` 1초가 여유로워서가 아니라 **기다릴 대상이 없기 때문이다** —
재초기화 버스트(7.4.1)가 지나면 좌석이 전부 `SOLD`가 되고, 그 뒤 120초 동안
아무도 행 락을 쥐지 않아 `FOR UPDATE`가 즉시 성공한다.

그 결과 **7.5의 사전 가설을 시험할 조건이 만들어지지 않는다.** 가설이 지목한
비용은 "비관적 락이 **대기하는 동안** DB 커넥션을 쥔다"인데, 대기 자체가
없으면 그 비용도 없다. `redis`가 이 조건에서 `pessimistic`을 이겨도 가설이
검증된 것이 아니다.

**같은 문제가 남은 세 전략에도 그대로 온다.** `optimistic`의 재시도·
`RETRY_EXHAUSTED`, `unique`의 제약 위반은 전부 "좌석을 두고 실제로 겨루는
구간"에서만 값을 갖는다. 그 구간이 수십 밀리초뿐이면 세 열이 모두 0 근처로
붙어 전략 비교가 성립하지 않는다.

**그래서 `optimistic` 구현 전에 이 시나리오를 확정한다.** 나중에 추가하면
`none`과 `pessimistic`을 다시 재야 한다.

##### 좌석 회수 방법 — 세 안 비교

락 대기를 유지하려면 좌석이 소비되는 속도만큼 돌아와야 한다.

| 방법 | 회수 속도 | **전략 중립성** | 요청 구성 | 증거 보존 |
|---|---|---|---|---|
| **홀드 해제** | 소비 속도에 **자동으로 맞춰진다** | 중립 — `DELETE /api/holds/{holdId}`는 전략 밖 공통 경로다 | 요청 종류 +1 | V-1이 무너진다 (아래 V-6으로 대체) |
| TTL 만료 | 고정·느리다. 10석 × TTL 10초 = 초당 1석 | **비중립 — 기각 사유** | 변화 없음 | 유지 |
| 별도 리셋 | 조절 가능하나 버스트형 | 중립 | 변화 없음 | 리셋이 증거를 지운다 |

**TTL 만료를 기각하는 이유가 결정적이다.** 만료된 홀드를 실제로 회수하는
주체는 전략별 홀드 경로이고, erd.md 4.1의 전략별 표가 그 시점을 다섯 가지로
다르게 정해 두었다 — **`none`은 아예 회수하지 않는다.** 청소 스케줄러는 아직
구현돼 있지 않으므로 만료만으로 좌석이 돌아오는 경로 자체가 없다. 회수
메커니즘이 전략마다 다르면 회수 속도가 전략마다 달라지고, 그러면 **측정하려는
락 대기가 아니라 회수 속도 차이를 재게 된다.**

**별도 리셋을 기각하는 이유는 증거와 잡음이다.** 측정 구간 안에서 주기적으로
재고를 되돌리려면 홀드·예약 행도 함께 정리해야 하는데, 그러면 초과 확정 증거가
매 주기 지워진다. 정리하지 않고 재고만 되돌리면 확정 예약이 계속 쌓여 V-1이
회수 횟수만큼 거짓 양성을 낸다. 게다가 리셋 자체가 경합 중인 바로 그 행에
쓰기를 하므로, 측정 구간 한복판에 전략과 무관한 쓰기 경쟁을 주기적으로
집어넣게 된다.

##### 채택 — 홀드 후 즉시 해제

한 반복은 **`POST /api/holds` → 성공하면 `DELETE /api/holds/{holdId}`** 두
요청이다. 확정하지 않는다.

- **회수가 소비를 자동으로 따라간다.** 잡은 사람이 곧 반납하므로 재고가
  마르지 않고, 별도 조절 장치가 필요 없다.
- **회수 경로가 전략 밖 공통 코드다.** `SeatHoldService#release`는 5개 전략이
  동일하게 쓴다. 회수 속도에 전략 차이가 섞이지 않는다.
- **확정을 빼는 것이 의도다.** 7.5가 말하는 것은 **락 획득**(CS-1)이고,
  확정을 넣으면 요청 종류가 셋이 되어 p95가 무엇의 응답시간인지 흐려진다.
  CS-2·CS-3 경합은 경합도 3단계와 Mock PG 지연 시나리오(7.3)가 담당한다.

###### `f` 공식이 틀렸던 이유

처음 적은 식은 분자를 **초당 회수 횟수**로 잡았다. 틀렸다. 행 락은 회수에
성공한 요청만 잡는 것이 아니라 **모든 시도가 잡는다** — 거절되는 요청도
`FOR UPDATE`로 행을 잡고 상태를 읽은 뒤 놓는다. 대기를 만드는 것은 그쪽이다.

```
ρ = (초당 시도 ÷ 좌석 수) × 요청당 행 락 점유 시간
```

**두 가지 점유를 구분하지 않은 것이 근본 원인이다.**

| 구분 | 지속 시간 | 3석 실측 |
|---|---|---|
| **논리적 점유** (`HELD` 상태) | 홀드 커밋 → 해제 커밋, 왕복 한 번 ≈ 24ms | 좌석당 82% |
| **행 락 점유** (`FOR UPDATE`) | 트랜잭션 안에서만 ≈ 0.2~2ms | 좌석당 33% |

거절률을 만드는 것은 앞의 값이고, 락 대기를 만드는 것은 뒤의 값이다.
**행 락은 커밋 시점에 풀리므로 좌석이 논리적으로 잡혀 있는 동안에도 대부분
자유롭다.** 좌석을 3석 → 1석으로 줄여도 좌석당 회전이 함께 줄어 `ρ`가 크게
오르지 않는다(파일럿 1~3). **좌석 수는 이 시나리오의 유효한 손잡이가 아니다.**

###### 손잡이를 도착률로 바꿨다

`ρ`의 분자는 초당 시도이므로 좌석 수보다 **도착률**이 직접적인 손잡이다.
`sleep`을 1000ms → 50ms로 줄이자 시도가 491/s → 3,484/s로 늘고 홀드 p95가
47ms → 236ms가 됐다. **응답시간의 대부분이 락 대기이며, 이것이 원래 재려던
값이다.**

`sleep`과 VU는 7.2가 못박은 값이 아니다. 7.2의 표가 고정한 것은 경합도 3단계의
좌석 수와 VU이고, 7.2.2가 처음에 500 VU·1초를 쓴 것은 고경합과 맞춘 선택이었다.
**0으로는 두지 않는다** — 완전한 폐루프가 되면 도착률이 서버 처리량에 종속되어
손잡이 자체가 사라진다.

###### 대안으로 검토했다가 기각한 것 — `lock_timeout` 낮추기

지속 경합 시나리오에서만 `lock_timeout`을 낮추면 포기가 생긴다. **기각한다.**

7.5가 재려는 비용은 "대기하는 동안 커넥션을 쥔다"이고 그 크기는 **대기 시간에
비례한다.** 상한을 낮추면 포기율이라는 숫자는 얻지만 커넥션 점유도 함께 잘려,
**지표를 만들면서 재려던 값을 파괴한다.** `redis`와의 비교에서 더 나쁘다 —
가설은 두 전략의 점유 차이를 보려는 것인데 상한이 짧으면 차이가 그만큼 줄어
가설이 참이어도 보이지 않는다. 7.3 고정 변수를 시나리오별로 쪼개면 두 시나리오의
락 포기율을 같은 의미로 읽을 수도 없게 된다.

###### 결론 — 목표를 실제 판정 기준으로 되돌린다

**락 포기율 1~20%라는 목표를 폐기한다.** 포기율이 재려던 것은 "대기가
충분한가"였는데, 확정 설정에서 포기는 0건이다.

> ⚠ **여기서 한 판단이 나중에 틀린 것으로 드러났다.** 당시 나는 "응답시간의
> 대부분이 이미 락 대기이므로 대기는 충분하다"고 적었다. `sleep`을 낮추자
> p95가 47ms → 236ms가 된 것을 락 대기로 읽은 것이다. **틀렸다.** 그 상승은
> 도착률이 오르며 생긴 애플리케이션 대기열이었고, 락이 아예 없는 `none`을 같은
> 설정으로 돌리자 239ms가 나와 정정됐다. 원인은 **보정 파일럿을
> `pessimistic` 하나로만 돌린 것** — 7.4.2가 본 측정에 요구한 대조군 규칙을
> 파일럿에는 적용하지 않았다. **보정 파일럿에도 대조군을 넣는다.**
> 전말은 [`results/sustained-lock-wait-investigation.md`](results/sustained-lock-wait-investigation.md) 4절.

**오히려 포기가 0인 편이 낫다.** 7.6.1의 함정 — 포기한 요청이 상한에서 빨리
빠져나가 p95가 좋아 보이는 현상 — 이 성립하지 않으므로 **두 전략의 홀드 p95를
직접 비교할 수 있다.** 포기가 섞이면 그 비교부터 무너진다.

**판정 기준은 7.5의 커넥션 풀 지표다**(아래). 포기율은 참고 열로 남긴다.

##### 지표와 판정 — 7.6 표에 섞지 않는다

**p95의 의미가 다르다.** 경합도 3단계의 p95는 매진 이후 거절이 대부분을
차지하는 값이고(`results/p95-inversion-investigation.md`), 이 시나리오의 p95는
**락을 기다린 시간이 실제로 들어 있는 값**이다. 같은 열에 놓으면 두 숫자가
같은 것을 재는 것처럼 보인다. 별도 표로 기록한다.

| 열 | 출처 | 이 시나리오에서의 의미 |
|---|---|---|
| **홀드 p95 / p99** | k6, `operation=hold` 태그만 | 락 대기가 포함된 응답시간. **해제 요청은 제외한다** |

> 점유 구간이 아니라는 뜻이므로 가설은 기각한다.

**점유(`usage`)를 1차 지표로, 대기(`acquire`)를 2차 지표로 읽는다.** 가설이
말하는 것은 "대기하는 동안 커넥션을 **쥔다**"이므로 전략이 직접 결정하는 값은
점유 시간이다. 획득 대기는 그 결과이며 도착률·풀 크기에도 함께 좌우된다.
확정 설정 실측에서 `pessimistic`의 점유는 5.32ms인데 획득 대기는 19.75ms로
**대기가 점유보다 크다** — 이 부하에서는 풀 압력의 상당 부분이 락 점유가 아니라
요청량에서 온다. 두 전략을 비교할 때 `acquire` 차이만 보면 그 공통분을 전략
차이로 오해한다. **점유 차이가 먼저 있어야 대기 차이를 전략 탓으로 돌릴 수 있다.**

**포기율은 판정에 쓰지 않는다.** 확정 설정에서 0건이고, 그것이 정상이다.
0이기 때문에 7.6.1의 함정(포기가 많을수록 p95가 좋아 보인다)이 성립하지 않아
**두 전략의 홀드 p95를 직접 비교할 수 있다.**

###### 실측 결과 — 이 기준으로는 판정할 수 없었다

**7.5는 이 조건에서 검증 불가다.** `pessimistic`의 커넥션 점유가 `none`보다
0.010ms 높을 뿐이다 — **가설이 전제한 "대기하는 동안 커넥션을 쥔다"는 비용을
지불한 적이 없다.** 행 락이 커밋 시점에 풀려서, 좌석이 논리적으로 잡혀 있는
동안에도 다른 요청은 기다리지 않고 `FOR UPDATE`로 잡아 "이미 HELD"를 보고
즉시 나온다.

**반증이 아니다.** 조건이 성립하지 않았으므로 예측을 시험한 적이 없다.
`redis`가 이 조건에서 이겨도 검증이 아니라고 적었던 것과 같은 규율이다.

**그래서 이 시나리오를 4.5.1 검증용으로 재배치한다**(아래 7.5.1).

**해석 순서를 고정한다.** 락 포기율이 높은 전략일수록 포기한 요청이 상한에서
빨리 빠져나가 p95가 좋아 보인다(7.6.1). 이 시나리오는 포기가 실제로 발생하는
조건이므로 **p95를 락 포기율과 함께 읽어야 하며, 포기율이 다른 두 전략의 p95를
직접 비교하지 않는다.**

##### 정합성 검증 — V-1 대신 V-6

해제하면 예약이 `CANCELLED`가 되어 `status='CONFIRMED'`만 세는 V-1이
구조적으로 0이 된다. 이 시나리오에서는 **점유 구간이 겹쳤는지**를 본다.

예약 하나의 점유 구간은 `[created_at, cancelled_at)`이다. 예약 행은 홀드 시점에
만들어지고(erd 4절) 해제 시 `CANCELLED` + `cancelled_at`이 찍힌다. 아직 살아
있는 홀드는 끝이 없으므로 `infinity`로 둔다.

**쌍끼리 조인하지 않는다.** 이 시나리오는 좌석 몇 개에 수만 건의 예약을 쌓으므로
self-join이 좌석당 O(n²)로 폭발한다 — 3석에 1만 건씩이면 1.5억 쌍이다. 실측
파일럿에서 30초 만에 좌석당 1,956회가 돌았다. 좌석별로 시작 시각 순으로 훑으며
**앞선 구간들의 최대 종료 시각과만** 비교하면 O(n log n)으로 같은 답을 얻는다.

```sql
-- V-6 점유 구간 중첩: 같은 재고 행을 두 예약이 동시에 점유한 적이 있는가.
SELECT count(*) FROM (
  SELECT r.created_at,
         max(coalesce(r.cancelled_at, 'infinity'::timestamptz))
           OVER (PARTITION BY rs.seat_inventory_id
                 ORDER BY r.created_at
                 ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS prev_end
  FROM reservation_seat rs
  JOIN reservation r ON r.id = rs.reservation_id
  JOIN seat_inventory si ON si.id = rs.seat_inventory_id
  WHERE si.session_id = :session_id
) t
WHERE t.prev_end IS NOT NULL AND t.created_at < t.prev_end;
```

구현은 `load-test/sql/verify-sustained.sql`에 있으며, 회수 누수 검증(L-1·L-2)도
같은 파일에 있다.

**검수 기준의 정본은 여전히 경합도 3단계다.** 이 시나리오는 락 대기 특성을
재기 위한 것이고, V-6은 회수를 섞은 상태에서도 초과 점유가 없었는지 확인하는
보조 검증이다. `none`에서는 0이 아니어야 정상이다.

##### 회수가 새면 시나리오가 무효다

홀드에 성공했는데 해제에 실패하면 그 좌석은 TTL이 만료될 때까지 순환에서
빠지고, 스케줄러가 없으므로 사실상 영구히 빠진다. 그런 누수가 쌓이면 재고가
말라 **다시 매진 상태 측정으로 되돌아간다.**

- k6는 홀드 성공 뒤 **반드시** 해제를 호출하고, 실패하면 회수 성공률에 센다.
- 회수 성공률이 1에서 유의하게 떨어지거나 종료 시점 재고에 `HELD`가 남아 있으면
  **그 실행을 폐기한다.** 재초기화 실패(7.4.1)와 같은 등급의 무효 사유다.

##### 실행 순서

1. ~~`pessimistic`으로 파일럿 — 설정 보정~~ **완료**. 좌석 1석 / VU 500 / `sleep` 50ms
2. `none`·`pessimistic`을 이 시나리오로 측정한다 ← **다음**
3. 그다음에 `optimistic`을 구현한다

**2번을 건너뛰고 `optimistic`으로 넘어가지 않는다.** 시나리오를 나중에
추가하면 앞의 두 전략을 다시 재야 한다.

##### `none`이 이 시나리오에서 보여야 하는 것

`none`은 성능 비교 대상이 아니라 대조군이다. 두 가지가 **반대로** 나와야 한다.

| 지표 | `none` 기대 | `pessimistic` 실측 |
|---|---|---|
| **V-6 점유 구간 중첩** | **0이 아니어야 한다** — 락이 없으니 같은 좌석을 동시에 점유한다 | 0 |
| 홀드 p95 | 낮다 — 기다리지 않는다 | 236ms (대부분이 락 대기) |
| 커넥션 점유(`usage`) | 낮다 — 대기 구간이 없다 | 5.32ms |
| 정상 거절(409) | 낮다 — 거절할 근거를 확인하지 않는다 | 99.4% |
| 회수 성공률·L-1·L-2 | 100% · 0 · 0 (동일) | 100% · 0 · 0 |

**V-6이 0이면 그 실행을 의심한다.** 락 없는 구현이 좌석 1석에 500 VU를 붙였는데
점유가 한 번도 겹치지 않았다는 뜻이므로, U-2가 지워지지 않았거나(`seed.sh`는
`none`일 때만 지운다) 시나리오가 의도대로 돌지 않은 것이다.

**`none`의 홀드 p95를 `pessimistic`보다 "좋다"고 읽지 않는다.** 기다리지 않아서
빠른 것이고, 그 대가가 V-6이다. 경합도 3단계에서 같은 오해를 한 기록이
`results/p95-inversion-investigation.md`에 있다.

**사용자 수는 VU 수와 다르다.** 둘을 같게 두면 저경합에서 1인 최대 매수(4매)가
좌석보다 먼저 바닥난다 — 100 VU × 4매 = 400석이라 1000석 중 600석이 손도 닿지
않은 채 남은 요청이 전부 `QUOTA_EXCEEDED`가 되고, 7.2가 저경합에서 보려는 좌석
경합 대신 할당량 거절을 재게 된다. 실측에서 100개 할당량 행이 전부 4에서
포화했다.

| 시나리오 | 좌석 | VU | **사용자 수** | 근거 |
|---|---|---|---|---|
| 저경합 | 1000 | 100 | **400** | 1000석 ÷ 4매 = 250명이 있어야 재고를 다 소화한다. 여유 1.6배 |
| 고경합 | 10 | 500 | **500** | 좌석이 10석뿐이라 할당량은 애초에 걸리지 않는다. 동시에 도는 VU가 같은 할당량 행을 다투지 않도록(CS-6 직렬화가 좌석 경합에 섞이지 않도록) VU 수에 맞춘다 |
| 극단 | 1 | 200 | **200** | 같은 이유 |

**해결책은 사용자 수를 늘리는 것이지 `max_per_user`를 올리는 것이 아니다.**
상한 4매는 REQ-03이자 CS-6의 검증 대상이다. 그 값을 키우면 V-3(매수 상한 초과)
검증이 형식만 남는다. 사용자 수는 요구사항이 아니라 시나리오 설계 변수이므로
이쪽을 움직인다. k6는 실행 전체에서 고유한 반복 번호로 사용자 풀을 순회한다 —
VU 번호를 그대로 쓰면 VU 하나가 실행 내내 같은 사용자여서 같은 문제가 남는다.

**k6가 앱과 같은 머신에서 돈다.** 이 표가 요구하는 "앱과 분리된 호스트"는 로컬
측정에서 충족되지 않는다. k6 컨테이너와 앱 2대·Postgres·Redis가 같은 Docker
호스트의 CPU를 나눠 쓰므로, 부하 생성 비용이 측정 대상과 자원을 다툰다. 고경합
500 VU처럼 부하 생성 자체가 무거운 구간에서 응답시간이 실제보다 나쁘게 나올 수
있다. **전 전략이 같은 조건이라 전략 간 비교는 유효하지만, p95 절댓값을 검수
기준 3초와 직접 대조할 때는 이 제약을 함께 읽는다.** 3개월차 AWS 환경에서는
k6를 별도 인스턴스로 분리해 다시 잰다.

**검수 기준 p95 3초 = 락 대기(최대 1초) + DB 처리 + 앱 처리 + 네트워크.** 이 예산이 Redisson `waitTime`과 Postgres `lock_timeout`을 둘 다 1초로 묶는 근거다. 락 대기 상한이 예산 전체를 먹으면 나머지 구간이 아무리 빨라도 REQ-10을 만족할 수 없다.

**`lock_timeout`을 명시하지 않으면 무한 대기다.** 비관적 락은 대기하는 동안 DB 커넥션을 쥐고 있으므로(4.2), 상한이 없으면 커넥션 풀이 먼저 마르고 측정 대상이 락 경합에서 커넥션 고갈로 바뀐다. `deadlock_timeout` 200ms도 이때는 도움이 되지 않는다 — 데드락 탐지기는 순환 대기만 잡고, 데드락이 아닌 단순 경합 대기는 그대로 두기 때문이다. 두 설정은 같은 층위의 측정 영향 변수이며 함께 고정한다.

**커넥션 풀 크기가 이 표에서 가장 위험하다.** 기본값 10에 VU 500을 때리면 비관적 락 대기가 아니라 커넥션 대기를 측정하게 된다. 전 전략 동일 값을 쓰고 보고서에 그 값을 명시한다.

**로드밸런서도 같은 함정을 갖는다.** nginx `worker_connections` 기본값은 512인데,
nginx는 커넥션 하나를 클라이언트 쪽과 업스트림 쪽 **양쪽**으로 센다. 고경합
500 VU면 최소 1000개가 필요해 512에서 막히고, nginx가 커넥션을 리셋한다. k6는
그것을 status 0으로 받아 오류율에 넣으므로(`classify.js`) **앱이 5xx를 하나도
내지 않았는데 오류율 임계값이 깨져 그 실행을 버리게 된다.** 실측에서 고경합
1회차에 `512 worker_connections are not enough` alert이 394건 찍혀 실행 하나를
폐기했고, 같은 조건을 유지하려고 저경합까지 포함해 9회 전부를 다시 돌렸다.
커넥션 풀과 같은 층위의 측정 영향 변수이며, 로드밸런서가 병목이면 측정 대상이
락 전략이 아니라 nginx가 된다.

가상 스레드를 켜면 스레드 풀 상한이 사라지고 커넥션 풀이 유일한 병목이 되어 성능 특성이 달라진다. 본 측정에서는 기본값(비활성)을 유지하고, 4개월차에 여유가 있으면 별도 실험으로 다룬다.

**Mock PG 지연을 락 전략 비교 시나리오에 섞지 않는다.** `holdfast.mock-pg.callback-delay-ms`를 키우면 만료-확정 경합(CS-2·CS-3)을 결제 축에서 재현할 수 있지만(`state-transitions.md` 5.2), 그 지연이 섞인 채로 락 전략을 비교하면 어느 지연이 락 대기이고 어느 지연이 결제 지연인지 구분할 수 없어 측정이 오염된다. 락 전략 비교의 5개 행(7.6)은 전부 `outcome=approve`·지연 0으로 고정하고, Mock PG 지연 재현은 별도 시나리오로 분리한다.

#### 7.4.1 본 측정 시작 시 시드를 다시 초기화한다

**좌석은 유한 자원이고 확정된 좌석은 돌아오지 않는다.** 그래서 워밍업 30초가
재고를 전부 소모해 버리고, 정작 측정 구간에는 경합이 남지 않는다. 이 단계를
넣기 전 실측에서 세 경합도 모두 이렇게 나왔다.

| 시나리오 | 측정 구간 성공 | 409 내역 | 초과 확정(V-1) | 종료 시 재고 |
|---|---|---|---|---|
| 저경합 1000석/100VU | **0건** | `QUOTA_EXCEEDED` | 0 | SOLD 400 / AVAILABLE 600 |
| 고경합 10석/500VU | **0건** | `SEAT_ALREADY_SOLD` | 1 | SOLD 10 |
| 극단 1석/200VU | **0건** | `SEAT_ALREADY_SOLD` | **0** | SOLD 1 |

**워밍업의 목적은 JIT과 커넥션 풀을 데우는 것이지 경합 구간을 버리는 것이
아니다.** 유한 자원이 섞이면서 그 목적과 실제 효과가 어긋났다. 재초기화는
워밍업의 원래 의도를 살리면서 경합을 측정 구간으로 옮긴다.

**램프업이 도착을 직렬화하는 문제도 함께 풀린다.** 재초기화 없이는 좌석이
열려 있는 유일한 시점이 실행 시작 직후인데, 그때는 VU가 아직 0에서 목표치로
올라가는 중이라 사실상 동시성 1로 첫 홀드가 처리된다. 극단 시나리오의 V-1이
0이었던 이유가 이것이다 — 앱에 남은 방어 때문이 아니다. 재초기화 시점에는 VU가
전부 올라와 있으므로 좌석이 열리는 순간 진짜 동시 도착이 발생하며, **실제
티켓팅 오픈 순간에 더 가깝다.**

재초기화 시점은 시나리오가 알린다. 워밍업 경계를 넘은 첫 요청이 표식을 찍고
`scripts/run.sh`가 그 줄을 보고 시드를 다시 돌린다. 호스트에서 시계로 재면
컨테이너 기동 시간만큼 어긋나 재초기화가 워밍업 안으로 들어갈 수 있고, 그러면
열린 재고를 워밍업이 도로 소모해 원래 문제로 돌아간다.

**대안으로 검토했다가 채택하지 않은 것: 취소로 좌석 회수.** 매 반복마다
홀드→확정→취소하면 좌석이 `AVAILABLE`로 돌아와 전 구간 지속 경합이 된다.
그러나 요청 종류가 셋이 되면 p95와 TPS가 "홀드+확정의 성능"이 아니라 혼합
워크로드의 성능이 되어, **검수 기준 p95 3초(REQ-10)를 무엇에 적용하는지가
모호해진다.** V-1이 `CONFIRMED`만 세는 것도 걸린다 — 취소된 예약이 빠져나가
실행이 끝난 뒤에는 0으로 읽힌다.

**측정 구간 후반이 매진 상태라는 사실은 남는다.** 재초기화는 경합을 측정 구간
안으로 옮길 뿐 좌석을 무한히 공급하지 않는다. 재고가 다시 소진된 뒤의 요청은
`SEAT_ALREADY_SOLD` 정상 거절이며, 그 구간의 p95는 "경합을 이겨낸 응답시간"이
아니라 "매진 판정 응답시간"이다. 결과 문서에 이 사실을 명시한다.

**재초기화에 `TRUNCATE`를 쓰지 않는다.** 실행 전 초기화(`sql/seed.sql`)는
`TRUNCATE ... RESTART IDENTITY CASCADE`로 충분하지만, 재초기화는 500 VU가
때리는 한복판에서 일어난다. `TRUNCATE`는 테이블마다 `ACCESS EXCLUSIVE` 락을
차례로 잡는데 진행 중인 앱 트랜잭션은 이미 다른 테이블에 `AccessShareLock`을
쥐고 있어 서로를 기다리는 순환이 생긴다. 실측에서 고경합 1회차와 저경합
3회차의 재초기화가 데드락으로 통째로 롤백됐고, **재고가 매진 상태로 남은 채
측정이 그대로 이어졌다**(고경합 성공 0건 · 저경합 성공 228건).

**재초기화가 조용히 실패하는 것이 이 단계에서 가장 위험하다.** 숫자는
그럴듯하게 나오는데 측정한 것이 다른 상태이기 때문이다. 그래서 두 가지를 함께
둔다 — 재초기화를 행 단위 DELETE/UPDATE로 바꿔(`sql/reset.sql`)
`RowExclusiveLock`만 잡게 하고, 실패하면 재시도한 뒤 그래도 안 되면 회차를
폐기하도록 `scripts/run.sh`가 `RESEED_FAILED`를 남긴다. 카탈로그(프로그램·
배치도·좌석·회차)는 실행 중에 바뀌지 않으므로 재초기화 대상이 아니다.

**재초기화는 대상 좌석을 먼저 잠근다.** 삭제와 재고 초기화 사이에 진행 중이던
홀드가 커밋하면, 그 행은 이미 지나간 DELETE를 피해 살아남는데 뒤이은 재고
UPDATE가 좌석을 `AVAILABLE`로 되돌린다. 살아남은 예약이 `CONFIRMED`면 그 좌석이
다시 팔려 **초과 확정이 만들어지고**(U-2는 `HELD`만 보므로 막지 못한다),
`HELD`면 다음 INSERT가 U-2에 걸려 **제약 위반이 오른다.** 저경합에서 두 현상이
함께 관측됐다. 트랜잭션 첫머리에서 좌석 행을 `ORDER BY seat_id`로
`FOR UPDATE` 잡으면 그 창이 닫힌다 — 순서는 5.1의 전역 락 순서와 맞춘 것이다.
전말은 [`results/reseed-artifact-investigation.md`](results/reseed-artifact-investigation.md).

**7.2.1의 데드락 검증은 이 흔적에 오염되지 않는다.** 그 시나리오는
`scripts/run-deadlock.sh` + `scenarios/deadlock.js`로 따로 돌며 재초기화 단계를
거치지 않는다. `pg_stat_database.deadlocks`를 판정에 쓰는 쪽과 재초기화를 쓰는
쪽이 분리되어 있어야, 0이 아닌 데드락 수를 5.1 위반으로 읽을 수 있다.

#### 7.4.2 전략은 세션을 나눠 재되, 같은 세션에 대조군을 하나 넣는다

`pessimistic` 측정에서 p95가 세 시나리오 전부 `none`보다 **낮게** 나왔다.
락을 걸었는데 더 빠르다는 결과라, 전략 차이인지 세션 간 변동인지부터 갈라야
했다. 두 전략이 40분 간격의 다른 세션에서 측정됐고 k6가 앱과 CPU를 공유하는
환경이기 때문이다(7.3 미충족).

**같은 세션에서 `none` 고경합 3회를 대조군으로 다시 돌려 판정했다.**

| 측정 | `none` 고경합 p95 중앙값 |
|---|---|
| 세션 1 (원래) | 39.74ms |
| 세션 2 (대조군) | 40.72ms |
| 세션 2 `pessimistic` | 31.82ms |

세션 간 변동은 1~3ms인 반면 같은 세션 안의 전략 간 격차는 8.9ms다.
**전략 간 차이는 실재하며, 전략별로 세션을 나눠 측정하는 방식 자체는
유효하다.** 한 세션에서 전략을 번갈아 돌리도록 바꾸지 않는다 — 전략을 바꾸려면
앱을 재기동해야 하고, 회차마다 재기동을 끼우면 JIT 워밍업(7.4-2)이 매번
초기화되어 더 큰 왜곡이 생긴다.

**대신 두 가지를 의무로 둔다.**

| 규칙 | 이유 |
|---|---|
| 회차마다 **커넥션 풀 대기**를 함께 기록한다 | 이 값이 없으면 p95 차이를 해석할 수 없다. 실제로 p95는 풀 대기의 거의 선형 함수였고, 그 값을 알면 전략 라벨이 아무것도 더해 주지 않았다 |
| 세션을 나눌 때 **이미 측정한 전략 하나를 같은 세션에서 다시 돌린다** | 세션 변동과 전략 차이를 가르는 유일한 방법이다. 대조군 없이는 위 판정을 내릴 수 없었다 |

남은 `optimistic`·`unique`·`redis`도 이 방식으로 측정한다. 대조군은
`none` 고경합 3회로 고정해 세 전략의 세션을 서로 비교할 수 있게 한다.

##### 대조군 전환이 앱 카운터를 지운다 — 회차마다 파일로 받는다

**대조군 규칙에는 부작용이 하나 있다.** 대조군으로 넘어가려면
`HOLDFAST_STRATEGY`를 바꿔 앱을 재기동해야 하는데, 7.1이 "앱 커스텀 메트릭"으로
출처를 못박은 값들은 **인스턴스 기동 시점부터 누적**이다. 재기동하는 순간
방금 측정한 전략의 커넥션 풀 대기·낙관적 재시도·제약 위반이 **통째로 사라진다.**

`pessimistic`·지속 경합·`optimistic`에서 연달아 같은 일이 났고, 매번 보강 측정을
다시 돌려 40분씩 썼다. 콘솔 출력만으로는 부족하다 — 로그를 파일로 받지 않으면
터미널 스크롤백과 함께 없어진다.

**그래서 `run.sh`가 회차 직후에 자동으로 파일에 받는다.**

| 파일 | 내용 | 시점 |
|---|---|---|
| `results/metrics-{전략}-{시나리오}-run{N}.json` | Actuator 지표 전부 (풀 대기·점유, 재시도, 소진, 제약 위반) | 회차 직후 |
| `results/verify-{전략}-{시나리오}-run{N}.txt` | V-1~V-5 | 회차 직후 |
| `results/metrics-{전략}-{시나리오}-run0.json` | 기준선 | 첫 회차 **전** |

**기준선(run0)이 필요한 이유**는 값이 누적이기 때문이다. 1회차의 증가분을 내려면
첫 실행 전 값이 있어야 한다. 회차별 값은 연속한 두 스냅샷의 차로 구한다.

**V-1·V-2도 같은 이유로 파일에 받는다.** 다음 회차의 시드가 DB를 덮으므로,
그때 받아두지 않으면 그 회차의 값을 되찾을 방법이 없다.

**`—`와 `0`을 구분해 기록한다.** 낙관적 재시도는 `optimistic` 전략의 빈이
만드는 메트릭이라 다른 전략에서는 아예 존재하지 않는다. 스냅샷은 이 경우를
`null`로, "메트릭은 있는데 값이 0"인 경우를 `0`으로 남긴다 — 7.6 표의
`—`(해당 없음)와 `0`(쟀는데 0)이 섞이지 않게 하기 위해서다.

이 파일들은 원본이므로 커밋하지 않는다. 채택본만 `docs/results/`로 옮긴다.

**이 조사의 전말은 [`results/p95-inversion-investigation.md`](results/p95-inversion-investigation.md)에 있다.**
작업량 가설을 세우고 성공 건수와 코드 경로로 반증한 기록이며, "락을 걸었더니
빨라졌다"로 읽히지 않게 하는 것이 그 문서의 목적이다.

**본 측정 길이는 두 값을 구분해 쓴다.**

| 용도 | 길이 | 쓰는 때 |
|---|---|---|
| 개발 확인용 | **30초** (기본값) | 시나리오·집계를 고치면서 반복 실행할 때 |
| 최종 측정용 | **120초** | 보고서에 실을 숫자를 뽑을 때 |

**120초는 JIT가 안정화된 뒤에도 충분한 표본을 쌓기 위한 길이다.** 워밍업 30초로
JIT 컴파일이 끝나도 p95·p99는 꼬리 분포라 표본이 적으면 실행마다 크게 흔들린다.

**30초를 기본값으로 두는 이유는 전체 실행 시간이다.** 5전략 × 3회 × 3시나리오 =
45회이고, 회차마다 워밍업 30초가 붙는다. 최종 측정용 120초로 전부 돌리면
45 × 150초 = 약 1시간 52분에 시드·기동 시간까지 더해져 두 시간을 넘는다. 개발
중에 매번 이 시간을 쓸 수는 없다. 30초면 45 × 60초 = 45분이다.

**개발 확인용 실행의 숫자는 보고서에 싣지 않는다.** 표본이 부족해 p99가 특히
불안정하다. 7.6 기록 양식을 채우는 것은 120초 실행뿐이다.

**JVM 워밍업은 자바 특유의 함정이다.** JIT 컴파일 전 첫 수천 요청은 눈에 띄게 느려서, 워밍업을 버리지 않으면 첫 번째로 측정한 전략이 무조건 손해를 본다. GC 일시정지는 p95보다 p99 꼬리를 흔들기 때문에 대표값으로 p95를 쓰되 p99도 함께 기록한다.

### 7.5 사전 가설

측정 전에 적어두고 나중에 대조한다.

> Redis 분산락이 p95에서 비관적 락을 앞설 것이다. Redis가 빨라서가 아니라, 락 획득을 트랜잭션 시작 **전에** 수행하면 대기 중 DB 커넥션을 점유하지 않기 때문이다. 비관적 락은 커넥션을 쥔 채 대기한다.

검증하려면 `hikaricp.connections.pending`을 함께 기록해야 한다. 그래야 결론이 "Redis 승"이 아니라 "자원 점유 구간의 차이"가 된다.

**현재 시나리오로는 이 가설을 시험할 수 없다.** 가설이 지목한 비용은 "비관적
락이 **대기하는 동안** 커넥션을 쥔다"인데, `pessimistic` 실측에서 락 대기가
사실상 발생하지 않았다(락 포기 0.01% 미만, 7.6.1). 재초기화 버스트가 끝나면
좌석이 전부 `SOLD`가 되어 아무도 행 락을 쥐지 않으므로 `FOR UPDATE`가 즉시
성공한다. **`redis`가 이 조건에서 `pessimistic`을 이겨도 7.5가 검증된 것이
아니다** — 가설이 말하는 비용을 `pessimistic`이 지불한 적이 없기 때문이다.
`redis` 측정 전에 락 대기가 지속되는 구간을 만드는 문제를 먼저 다뤄야 한다
(`results/m2-pessimistic.md` 5.1).

#### 7.5.1 지속 경합 시나리오를 4.5.1 검증용으로 재배치한다

7.5는 검증할 수 없지만, 같은 시나리오가 **4.5.1**을 검증하기에는 적합하다.

> **4.5.1** 이 락은 정합성을 보장하지 않는다 — 분산락은 성능 최적화이지 정합성
> 보장이 아니다.

이 명제는 락 대기가 필요 없다. 필요한 것은 **좌석 하나를 두고 요청이 끊임없이
겨루는 상태**이고, 그것은 이 시나리오가 실제로 만들었다 — `none`이 120초에
17,269건의 점유 중첩을 냈다.

**판정 기준은 제약 위반이다.**

| 결과 | 해석 |
|---|---|
| `redis`에서 **제약 위반(U-2) > 0** | **4.5.1 실증.** 분산락이 샜고 DB 제약이 막았다 |
| `redis`에서 V-6 > 0 | 더 나쁘다. U-2마저 막지 못했다 |
| 둘 다 0 | **반증이 아니다.** "이 부하·이 설정에서는 새지 않았다"까지만 말한다 |

**V-6이 아니라 제약 위반이 1차 지표인 이유**는 U-2가 걸려 있기 때문이다.
`redis` 락이 새어 두 요청이 같은 좌석을 홀드하려 하면 두 번째 INSERT가 U-2에
막혀 **제약 위반 카운터가 오르고 V-6은 0으로 남는다.** `none`은 U-2를 지우고
재므로(erd 3.1) 중첩이 V-6에 그대로 드러난다 — **`none`이 대조군인 것이 이
구조 때문이다.**

**둘 다 0일 때 반증이 아닌 이유도 분명히 한다.** Redisson 락이 새는 조건은 락
만료와 GC 정지 같은 것인데, 120초 실행에서 그 조건이 재현된다는 보장이 없다.
"새는 것을 관측하지 못했다"와 "새지 않는다"는 다르다.

**※ `none`의 초과 홀드 0은 "겹친 홀드가 없었다"는 뜻이 아니다.** V-2는 활성
홀드(`status='HELD'`)만 세는데 이 시나리오는 홀드 직후 확정하므로 HELD 창이
밀리초 단위다. 실행 중 267회를 표본 추출했지만 활성 홀드가 하나도 잡히지
않았다. 상태를 무시하고 세면 고경합 한 실행에서 **10석 중 5석에 홀드가 겹쳤고
한 좌석에 최대 6건**이 걸려 있었다. 7.6.2의 "`none`에서는 둘 다 0이 아니어야
한다"는 이 시차를 고려하지 않은 서술이며, **실행이 끝난 뒤 재는 한 V-2는
구조적으로 0이고 그 실패는 V-1로 옮겨 나타난다.**

**`none`의 p95가 좋은 것은 자랑거리가 아니다.** 락이 없으니 아무것도 기다리지
않을 뿐이고, 그 대가가 초과 확정이다. 락 전략 4종은 이 응답시간을 얼마나
지불하고 초과 확정을 0으로 만드는지로 평가된다 — 위 값은 **지불 전의 값**이다.

**초과 확정 건수는 중앙값 하나로 요약하면 안 된다.** 회차마다 두 배씩 흔들린다
(저경합 2~4, 고경합 3~5, 한 좌석 최대 중복 2~4). 경합 승자가 몇 명 겹치느냐는
스케줄러가 그 순간 어느 스레드를 깨웠는지에 달렸기 때문이다. 이 열의 판정은
"몇 건이냐"가 아니라 **"0이 아니다"** 이며, 4종과 비교할 때도 그렇게 읽는다.

`none` 행의 제약위반 칸은 `—`다. 그 전략에서는 제약 자체를 걸지 않는다(2.1). 나머지 4개 행에서 이 값이 0이 아니면 앱 락이 샌 것이고, `unique` 행에서는 0이 아닌 것이 정상이다. 재시도 칸은 `optimistic`에만 값이 있다.

#### 7.6.1 락 포기율

**락 포기율은 정상 거절도 오류도 아니다.** 좌석이 이미 팔려 409를 반환한 것(409율)은 시스템이 제 역할을 한 결과이고, 5xx(오류율)는 고쳐야 할 결함이다. 락을 시간 안에 얻지 못해 포기한 것은 둘 중 어느 쪽도 아니다 — **좌석이 남아 있었을 수도 있는데 기다리다 포기한 것**이기 때문이다. 7.1의 분리를 지키려면 열을 따로 두는 수밖에 없다. 이 값은 409로 응답하지만 409율에 넣지 않는다.

세는 대상이 전략마다 다르고, **오류 코드로 구분된다.** 시간 기반 포기는 `LOCK_TIMEOUT`, 횟수 기반 포기는 `RETRY_EXHAUSTED`다(`api-spec.md` 3.2).

| 전략 | 락 포기율이 세는 것 |
|---|---|
| `none` | — 앱 락이 없다 |
| `pessimistic` | Postgres `lock_timeout` 1초를 넘겨 행 락을 얻지 못한 요청의 비율 (`LOCK_TIMEOUT`) |
| `optimistic` | 재시도 상한 3회를 소진해 포기한 **요청**의 비율 (`RETRY_EXHAUSTED`). 재시도 칸은 누적 **횟수**라 단위가 다르다 — 아래 주의 참조 |
| `unique` | — 앱 락이 없다. 제약 위반으로 인한 거절은 409율이 담당한다 |
| `redis` | Redisson `waitTime` 1초 안에 락을 얻지 못한 요청의 비율 (`LOCK_TIMEOUT`) |

**`optimistic`에서 두 열을 중복 집계하지 않는다.** 재시도 칸과 락 포기율은 같은 사건을 서로 다른 단위로 본다. 재시도 칸은 실행 전체의 누적 재시도 횟수이고, 락 포기율은 3회를 다 쓰고도 실패한 요청의 비율이다. 한 요청이 3회 재시도 후 포기하면 재시도 칸에는 3이, 락 포기율에는 요청 1건이 더해진다. **두 값을 더하거나, 한쪽을 다른 쪽의 근거로 환산하지 않는다.**

**`pessimistic` 실측에서 이 값은 경합도와 무관하게 0에 수렴했다** — 저경합 2건,
고경합 1건, 극단 4건(각 3회 합계, 전부 0.01% 미만). 좌석 1석에 200 VU가 몰리는
극단에서도 늘지 않는다. `lock_timeout` 1초가 여유로워서가 아니라 **기다릴 대상이
거의 없기 때문이다.** 재초기화 버스트가 지나면 좌석이 전부 `SOLD`가 되어 아무도
행 락을 쥐지 않고, 경합도를 올려도 버스트 길이는 늘지 않는다. 아래 함정이
`pessimistic` 행에는 적용되지 않는 이유이기도 하다 — 일찍 빠져나간 요청이 애초에
없다. **다만 이 결론은 `optimistic`·`redis`로 이월되지 않는다.** 그 둘은 재시도
상한과 `waitTime`이라는 다른 포기 경로를 갖는다.

**이 값이 0이 아니면 그 부하에서 처리 능력을 넘긴 것이다.** 락을 얻지 못한 요청이 나온다는 것은 경합이 그 전략의 처리량을 초과했다는 뜻이므로, 해당 경합도 행은 "동작했다"가 아니라 "여기서 한계에 닿았다"로 읽는다.

**p95는 반드시 락 포기율과 함께 읽는다.** 여기에 해석의 함정이 있다. 포기한 요청은 상한 시간에 걸려 **빨리** 실패하므로 응답 시간 분포에서 일찍 빠져나간다. 그래서 **락 포기율이 높은 전략일수록 p95가 오히려 좋아 보일 수 있다.** 락 포기율이 0이 아닌 행의 p95는 "끝까지 처리된 요청들의 p95"가 아니라 "일찍 포기한 요청이 섞여 낮아진 p95"다. 이 열을 빼놓고 p95만 비교하면 가장 빨리 포기하는 전략이 가장 빠른 전략으로 보고서에 남는다.

#### 7.6.2 초과 확정과 초과 홀드를 나눠 센다

한 열에 뭉쳐 두면 어느 쪽을 센 숫자인지 모호해진다. 둘은 심각도도 근거 쿼리도 다르다.

| 열 | 근거 | 의미 | 목표 |
|---|---|---|---|
| **초과 확정** | `verify.sql` V-1 | 같은 재고 행이 두 건 이상의 확정된 예약에 팔렸다 | **0 — 검수 기준**(REQ-01, 국립 SFR-001의 "초과 승인 0건") |
| **초과 홀드** | `verify.sql` V-2 | 같은 좌석에 활성 홀드가 둘 이상이다 | 0. 단 `none`은 실패 증거이므로 0이 아니어야 정상 |

**검수 기준에 직접 대응하는 것은 초과 확정이다.** 초과 홀드는 그 앞 단계이며, 홀드가 겹쳐도 확정에서 걸러지면 사용자는 좌석을 잃지 않는다 — 대신 아래의 팬텀 홀드율로 나타난다.

`none`에서는 **둘 다 0이 아니어야 한다.** 확정까지 순진하게 구현하는 이유가 그것이다(`state-transitions.md` 2.1절). 나머지 4개 전략에서는 둘 다 0이어야 하며, 초과 확정이 0이 아니면 그 전략은 검수 기준을 통과하지 못한 것이다.

#### 7.6.3 팬텀 홀드율

**정의: 홀드에 201을 받았으나 확정에 실패한 요청의 비율.** 출처는 k6이며, 홀드 성공 → 확정 실패 시퀀스를 태깅해 센다. 분모는 **홀드에 성공한 요청**이다 — 홀드 단계에서 거절된 요청은 애초에 약속을 받지 않았으므로 제외한다.

"좌석을 잡았습니다"라는 응답을 받은 뒤 결제 화면에서 좌석을 잃는 사용자 경험을 재는 값이다. 초과 확정이 DB 상태로 드러나는 실패라면, 이 열은 **약속이 지켜지지 않은 비율**이다.

**`none`에서 이 값이 높을 것으로 기대하면 안 된다.** 2.1절대로 확정까지 순진하게 구현하면 홀드를 가진 전원이 확정에도 성공하므로, 경합이 아무리 심해도 확정이 실패하지 않아 팬텀 홀드는 0에 수렴한다. 대신 그 실패는 **초과 확정(V-1)** 으로 나타난다. 30스레드가 좌석 1석을 동시에 홀드·확정한 단위 경합 테스트에서 실제로 이렇게 나왔다.

| 확정 경로 | 초과 확정 | 팬텀 홀드 |
|---|---|---|
| 순진한 SELECT-후-UPDATE (`none`) | 홀드 30건이 전부 확정 → **V-1 발생** | 0 |
| 원자적 조건부 UPDATE (4개 전략) | 0 | 홀드가 겹친 만큼 발생 |

**두 값은 같은 결함의 서로 다른 출구다.** 확정을 원자적으로 막으면 초과 확정이 팬텀 홀드로 바뀔 뿐, 홀드 단계의 경합 자체는 그대로다. 그래서 `none`은 확정까지 순진해야 검수 기준(초과 승인 0건)을 실제로 위반하고, 그 위반이 이 프로젝트가 제거해 보일 결점이 된다.

**이 열이 유용한 곳은 나머지 4개 전략이다.** 팬텀 홀드율이 0이 아닌데 초과 확정이 0인 전략은, 홀드 단계에서 경합을 막지 못하지만 확정 단계나 제약이 막아내는 **계층 방어** 구조라는 뜻이다 — 4.5.1의 `redis`가 그 후보이며, "분산락은 성능 최적화이지 정합성 보장이 아니다"를 숫자로 뒷받침하는 자리가 여기다. 홀드 TTL이 짧은 시나리오에서는 만료로 인한 확정 실패도 이 값에 섞이므로, 0이 아닐 때는 원인이 경합인지 만료인지 함께 확인한다.

README의 측정 결과 표는 고경합 시나리오를 요약본으로 싣고, 전체는 이 문서에 둔다.

### 7.7 M3 결론 구조 — 예상과 남은 전략에서 볼 것

**이 절은 측정이 끝나기 전에 적는다.** 7.5와 같은 이유다 — 나중에 숫자를 보고
결론을 맞추면 무엇을 예상했는지 알 수 없게 된다.

#### 7.7.1 예상 결론

`none`과 `pessimistic` 측정이 뒷받침하는 진술이다.

> **"어느 전략이 빠른가"가 아니라 "성능은 대체로 비슷하고, 차이는 정합성 보장
> 방식과 운영 특성에 있다."**

| 근거 | 값 |
|---|---|
| 지속 경합 홀드 p95 | 239.80 vs 240.94ms — **0.5%** |
| 지속 경합 커넥션 점유 | 5.330 vs 5.340ms — **0.19%** |
| 경합도 3단계 p95 차이 | 실재했으나 **커넥션 대기열로 설명됐다**(`results/p95-inversion-investigation.md`) |
| 락 포기율 | 전 시나리오 0에 수렴 |
| **초과 확정(V-1)** | none 2·4·1 / **pessimistic 0·0·0** |
| **점유 중첩(V-6)** | none 17,269 / **pessimistic 0** |

**성능 지표는 노이즈 안에서 겹치고, 정합성 지표는 자릿수로 갈린다.**

근본 이유는 **이 응용의 임계 구역이 서브밀리초**라는 것이다. 홀드 트랜잭션은
인덱스를 탄 몇 개의 문장이고, 결제는 홀드·확정 분리로 임계 구역 밖에 있다(3절).
**락을 쥔 채 하는 일이 없으므로 락 대기가 응답시간을 지배할 구간이 없다.**
이것은 결함이 아니라 홀드 정책 설계의 결과이며, 오히려 그 설계가 옳았다는
증거에 가깝다.

**한계를 분명히 둔다 — 아직 2/5 전략만 쟀다.** 성능 차이가 나타날 수 있는
후보는 둘이며, 둘 다 락 대기가 아니라 **전략 고유의 추가 작업**이다.

- `optimistic` — 재시도는 같은 일을 다시 한다. 응답시간에 직접 더해진다
- `redis` — 락 획득에 네트워크 왕복이 추가된다

**예측한다.** 두 전략에서 p95 차이가 나온다면 원인은 락 경합 비용이 아니라 위
두 가지일 것이다. 틀리면 이 절을 정정한다.

#### 7.7.2 남은 세 전략에서 볼 것

p95 순위가 아니다.

| 볼 것 | 왜 | 출처 |
|---|---|---|
| **정합성 보장 방식** (앱 락 / 제약 / 재시도) | 성능이 비슷하다면 이것이 선택의 근거다 | 4.3·4.4·4.5 |
| **제약 위반 0인가** | 앱 레벨 방어가 실제로 작동했는지의 유일한 증거. `unique`는 0이 아닌 것이 정상 | 7.6, Postgres 로그 |
| **전략 고유 비용이 어디서 나타나는가** | `optimistic`의 재시도 횟수, `redis`의 락 포기·왕복 | 7.6.1, 앱 메트릭 |
| **실패 모드** | 무엇이 잘못되면 어떻게 드러나는가. **조용히 틀리는 전략이 가장 나쁘다** | V-1·V-6·제약 위반 |

**제약 위반을 k6 지표로 셀 수 없다는 점에 주의한다.** U-2 위반은 공통 핸들러가
409 `SEAT_HELD_BY_OTHER`로 바꾸고 `debug` 로그만 남겨 정상 거절과 구분되지
않는다. Postgres 로그의 `duplicate key ... "ux_seat_hold_active"`를 회차마다
세야 한다(`results/m2-pessimistic.md` 1.1).

## 8. 검증 방법

| 종류 | 도구 | 대상 |
|---|---|---|
| 단위 경합 테스트 | JUnit5 + `ExecutorService` + `CountDownLatch` | 전략별 N스레드 동시 홀드, CS-6 |
| 통합 테스트 | **Testcontainers** (Postgres + Redis) | 전 전략 |
| 부하 테스트 | k6, 앱 2대 | 측정 |

**H2를 쓰지 않는다.** `FOR UPDATE` 의미론이 Postgres와 달라 동시성 테스트가 통과해도 아무것도 보장하지 않는다. Testcontainers로 실제 Postgres·Redis를 띄우며 CI에서도 그대로 돈다.

**단일 인스턴스로 측정하지 않는다.** 앱 1대에서는 분산락이 왜 필요한지 증명할 수 없고, 프로젝트의 논지 절반이 사라진다.

### 8.1 잘라도 되는 것

일정이 밀리면 **Prometheus + Grafana를 먼저 자른다.** k6 요약 출력과 Actuator 메트릭 스냅샷만으로도 비교표는 완성되고 논지도 성립한다. Compose 서비스 2개와 대시보드 작성 시간이 절약된다.

절대 자르지 않을 것: 베이스라인 실패 데이터, 앱 2대 구성, 유니크 제약.
