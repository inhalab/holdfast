**졸업 프로젝트 설계 명세 및 구현 범위**
2인 / 4개월 / 4학년 2학기

## 0. 문서 목적

이 문서는 공개된 공공 발주 제안요청서에서 요구사항을 발췌해 정의한 자체 프로젝트의 설계 기준선이다. 무엇을 만들지, 어디까지 만들면 성공인지, 무엇을 만들지 않을지를 사전에 고정하는 것이 목적이다.

---

## 1. 요구사항 출처

두 건의 제안요청서를 서로 다른 역할로 사용한다. 두 시스템을 각각 구현해 합치는 것이 아니라, **하나의 시스템**을 만들되 문서의 역할을 나눈다.

| 문서 | 역할 | 사용 방식 |
|---|---|---|
| 국립중앙과학관 통합예약시스템 개선 사업 제안요청서 (2026.3) | 요구사항 원본 | 무엇을 만들지, 검수 기준이 무엇인지 정의 |
| 궁능유적본부 온라인 전산 발권 시스템 기능 개선 제안요청서 (2026.6) | 설계 레퍼런스 | 발권·검표 단계의 화면·데이터 상세를 보강 |

### 1.1 국립중앙과학관을 원본으로 삼은 근거

- SFR-001의 명칭이 「동시 접속 및 예약 프로세스 안정화」로, 본 프로젝트의 주제와 직결된다.
- 검수 기준이 정량적으로 명시되어 있다.
  - SFR-001: 동시접속 및 부하 테스트 조건에서 **정원 초과 승인 0건**, 중복 승인·비정상 확정 미발생
  - PER-002: 예약 신청·조회 화면 **3초 이내** 응답
  - SFR-002: 동일 조건 조회 시 통계·정산값이 메뉴 간 일치
- PER-001에 "예약 오픈 시 동시접속 환경", "트랜잭션 충돌 방지를 위한 동시성 제어"가 별도로 기술되어 있다.
- 결제·정산을 제외해도 SFR-001의 골격이 그대로 남는다.

### 1.2 궁능유적본부를 보조로만 쓰는 이유

발권 도메인 서술은 이쪽이 구체적이다. QR 모바일 티켓, 전자검표, 회차별 잔여인원, 관람권 종류 구분, 단체 요금 자동 적용, 예약 오픈 일시 설정이 명시되어 있다. 다만 정량 검수 기준이 사실상 없고(3초 응답 정도), 22개 궁·능 확대·다국어 4종·발권기 하드웨어·교통카드 연계 등 범위가 과도해 주축으로 삼을 수 없다.

### 1.3 전제

두 문서 모두 기존 시스템의 **기능개선** 계약이다. As-Is 시스템이 없는 상태이므로 실제로는 신규 구축이며, 본 프로젝트는 RFP의 이행이 아니라 "RFP에서 요구사항을 발췌한 자체 프로젝트"다. 제안서에는 이 관계를 명시한다.

> 본 프로젝트의 요구사항은 국립중앙과학관 통합예약시스템 개선 사업 제안요청서(2026.3)의 SFR-001, 002, 003, 004, 006 및 PER-001~002를 기반으로 정의하였다. 발권·검표 영역의 상세 요구는 궁능유적본부 온라인 전산 발권 시스템 기능 개선 제안요청서(2026.6)의 SFR-03을 참조하였다. 좌석 지정 예약은 원본 요구사항의 정원 기반 예약을 좌석 단위 점유로 확장한 것으로, 본 프로젝트의 자체 정의 요구사항이다.

## 2. 시스템 흐름

두 개의 서브시스템이 아니라 하나의 파이프라인이며, 도메인 모델도 하나다.

```
프로그램·회차 조회
   ↓
좌석 선택 (선점 / hold)
   ↓
예약 확정              ← 동시성 제어 지점
   ↓
결제 (Mock PG)
   ↓
QR 티켓 발급
   ↓
검표 · 입장 처리
```

앞의 세 단계는 국립 SFR-001이 근거이고, 뒤의 두 단계는 국립 SFR-004(입장 처리)에 궁능 SFR-03의 상세를 얹은 것이다.

## 3. 설계 단계에서 작성할 명세

### 3.1 요구사항 추적표

가장 먼저 만든다. RFP 항목과 자체 요구사항을 1:1로 매핑한다.

| 자체 ID | 요구사항 | 출처 |
|---|---|---|
| REQ-01 | 동시 예약 요청 시 정원·좌석 초과 확정 방지 | 국립 SFR-001 |
| REQ-02 | 실시간 잔여 좌석 검증 및 표시 | 국립 SFR-001, SFR-006 |
| REQ-03 | 중복 예약 방지 / 1인 최대 매수 제한 | 국립 SFR-001 |
| REQ-04 | 예약·결제 상태 정합성 검증 | 국립 SFR-002 |
| REQ-05 | 알림 발송 재시도 및 중복 발송 방지 | 국립 SFR-003 |
| REQ-06 | 회차별 입장 가능시간 검증 및 검표 처리 | 국립 SFR-004 |
| REQ-07 | QR 모바일 티켓 발급 | 궁능 SFR-03 |
| REQ-08 | 예약 오픈 일시 설정 | 궁능 SFR-05 |
| REQ-09 | 좌석 지정 선택 및 좌석 단위 점유 | 자체 확장 |
| REQ-10 | 응답시간 p95 3초 이내 | 국립 PER-002 |

이 표는 범위가 새는 것을 막는 장치이기도 하다. 표에 없는 기능은 만들지 않는다.

### 3.2 도메인 모델 (ERD)

```
프로그램 ─┬─ 회차 ─┬─ 좌석재고(회차 × 좌석)
          │        └─ 입장가능시간
          └─ 예약오픈정책

좌석배치도 ─ 구역 ─ 좌석

예약 ─┬─ 예약좌석 (N)
      ├─ 결제(Mock)
      └─ 티켓 ─ 검표이력

알림발송(Outbox)
```

**핵심 결정 사항:** 좌석재고를 `회차 × 좌석` 단위 행으로 **미리 생성**할지, 예약 시점에 생성할지. 미리 생성하면 `(회차ID, 좌석ID)` 유니크 제약과 행 단위 락을 그대로 쓸 수 있어 훨씬 안전하다. 이 프로젝트에서는 사전 생성을 권장한다.

### 3.3 상태 전이 다이어그램

구현 중에 상태가 무한히 늘어나는 것을 막기 위해 착수 전에 확정한다.

- **예약**: `선점 → 결제대기 → 확정 → 취소` / `선점 → 만료`
- **좌석재고**: `가능 → 선점 → 판매` / `선점 → 가능(만료)` / `판매 → 가능(취소)`
- **티켓**: `발급 → 사용` / `발급 → 무효(예약취소)`

### 3.4 동시성 설계서 — 본 프로젝트의 본체

별도 문서로 분리한다. 포함할 내용:

1. **임계 구역 식별**
   - 좌석 점유(hold) 획득
   - 회차 정원 차감
   - 취소 시 좌석 반환
   - 홀드 TTL 만료 처리
2. **전략 후보와 선택 근거**
   - 비관적 락 (`SELECT ... FOR UPDATE`)
   - 낙관적 락 (버전 컬럼)
   - DB 유니크 제약
   - Redis 분산락
3. **홀드 정책**: TTL 길이, 만료 처리 방식(스케줄러 / 지연 큐 / lazy 검증)
4. **멱등성 키 설계**: 예약 요청, 결제 콜백, 알림 발송

### 3.5 그 외 산출물

| 문서 | 내용 |
|---|---|
| API 명세 (OpenAPI) | 엔드포인트, 요청·응답 스키마, 오류 코드 |
| 부하 테스트 계획서 | 시나리오, 목표치, 측정 항목. 목표치는 RFP 문구를 그대로 인용 |
| 테스트 시나리오 목록 | 정상 / 경합 / 실패 / 중복 / 만료 |
| 화면 설계서 | 좌석 맵, 예약 확인, 티켓, 검표 화면 |

## 4. 구현 범위

### 4.1 반드시 구현 (전체 공수의 약 70%)

- 프로그램·회차 조회, 실시간 잔여석 표시
- 좌석 맵 조회 및 타인 선점 상태 반영
- 좌석 선점(hold)과 TTL 자동 만료
- 예약 확정 — 동시성 제어 적용 지점
- 1인 최대 매수 제한, 중복 예약 방지
- Mock PG (성공 / 실패 / 타임아웃 / 지연 주입 가능)
- QR 티켓 발급
- 검표: QR 검증 + 회차별 입장 가능시간 검증 + 중복 사용 차단
- 취소 시 좌석 반환
- 알림 Mock: Outbox + 재시도 + 중복 발송 방지
- 예약 오픈 시각 설정
- **부하 테스트 하네스** — 기능이 아니라 산출물
- 최소 관리자 화면: 회차 등록, 좌석배치 등록, 예약 현황 조회

### 4.2 여유가 되면

- 대기열 (오픈런 대응) — 구현 시 발표 설득력이 크게 올라간다
- 예약 ↔ 결제 정합성 대조 배치 (국립 SFR-002 대응)
- 비회원 예약 조회
- 노쇼 처리

### 4.3 구현하지 않음

제안서에 제외 사유를 명시적으로 기술한다.

| 제외 항목 | 사유 |
|---|---|
| 실제 PG 연동, 환불 수수료 계산, 정산 | 계약·심사 절차가 필요해 학부 프로젝트에서 실현 불가 |
| 관리자 권한 세분화, 감사 로그 (국립 SFR-005 / SFR-007) | 조직 구조 의존적이며 본 주제와 직접 관련이 없음 |
| 다국어, 웹접근성 인증, 전자정부 표준프레임워크 | 인증·검증 비용이 크고 핵심 논지와 무관 |
| 실제 SMS·카카오 발송 | 발송 대행 계약 필요. Mock으로 대체 |
| 물리 검표 단말 연동 | 하드웨어 확보 불가. 웹 기반 스캐너로 대체 |
| 통계 대시보드 고도화 | 범위 대비 학습 가치가 낮음 |

## 5. 주의사항

### 5.1 설계·구현상 함정

**만료와 확정의 경합이 가장 자주 터진다.**
홀드가 TTL로 만료되는 시점과 결제 완료 콜백이 도착하는 시점이 겹치면, 만료된 좌석이 확정되거나 결제는 됐는데 좌석이 없는 상태가 된다. 설계 단계에서 이 케이스를 명시적으로 다룬다. 발표에서 가장 좋은 소재이기도 하다.

**락 범위를 회차 단위로 잡으면 성능이 죽는다.**
좌석 단위로 잡아야 하지만, 그러면 여러 좌석을 한 번에 예약할 때 데드락 위험이 생긴다. 좌석 ID 정렬 후 순차 획득 같은 규칙을 사전에 정한다.

**분산락 해제는 반드시 트랜잭션 커밋 이후에 한다.**
커밋 전에 풀면 락을 걸지 않은 것과 같다. 흔한 실수이며 부하 테스트로만 발견된다.

**Redis 재고 캐시를 쓰더라도 DB 유니크 제약은 반드시 건다.**
캐시는 성능용이고 최후 방어선은 DB다. `(회차ID, 좌석ID)` 유니크 제약 하나가 초과 예약을 0건으로 만드는 실질적 장치다.

**시각 기준을 서버 시간으로 통일한다.**
예약 오픈 시각, 홀드 만료, 입장 가능 시간이 모두 시간 기반이다. 클라이언트 시계를 신뢰하면 전부 조작 가능해진다.

### 5.2 측정·검증상 주의

**단일 인스턴스로만 부하 테스트하면 분산락의 의미가 없다.**
최소 2개 인스턴스를 띄우고 측정한다. 그렇지 않으면 "왜 이 락 전략이 필요한가"에 대한 답이 사라진다.

**베이스라인을 먼저 만들고 실패를 기록한다.**
락 없는 버전으로 부하를 걸어 초과 예약이 몇 건 발생했는지 숫자로 남기는 것이 순서다. 처음부터 완성본을 만들면 비교 대상이 없어지고 프로젝트의 논지 전체가 무너진다.

### 5.3 일정 관리상 주의

**좌석 맵 UI에 시간을 쏟지 않는다.**
2인 4개월 프로젝트의 가장 흔한 실패 원인이다. SVG 좌석 배치를 다듬다가 정작 동시성에 손도 못 대는 경우가 많다. 좌석 맵은 격자 형태로 최소 구현하고, 여유가 생겼을 때 개선한다.

## 7. 최종 산출물

이 프로젝트의 결과물은 동작하는 시스템 그 자체가 아니라 **증거**다.

1. 락 전략별 비교표 (초과 예약 건수, p95 응답시간, 처리량)
2. 실패 재현 기록 — 락 없는 상태에서 무엇이 어떻게 깨졌는지
3. 요구사항 추적표와 검수 기준 충족 여부
4. 동시성 설계서
5. 동작하는 시스템

발표의 중심은 1번과 2번이다. "결점 민감도가 높은 도메인을 골랐고, 그 결점을 재현했으며, 측정 가능한 방식으로 제거했다"는 서사가 성립해야 한다.
